## B-001　录入网址后卡片始终显示「识别中」，看起来像「只爬到一张封面图」

- **严重程度**：高（核心链路，用户直接感知「这东西坏了」；且库中数据永久停在 `pending`，界面无任何出口）
- **报告时间**：2026-09-24 20:31（用户第二次反馈，第一次在手机端，表现形式相同）
- **状态**：取证完成 · 根因已定位 · **修复中**
- **关联**：`docs/构建记录.md` #053（待写）

### 现象

电脑端录入一个 gooood 网址，点了「收进灵感库」之后去做别的事／关了页面。回来看时：

- 卡片右上角一直转圈显示 **「识别中」**，持续十几分钟没有变化；
- 整张卡看起来**只有一张 cover 图**，标题是「未命名」，摘要位是「（没有文字内容）」；
- 用户的判断是「只有封面图片有爬取」，也就是以为服务端抓取半途失败。

手机端此前出现过同类情况。

### 取证

查的是**线上库与埋点**，不是界面推断。出问题那条是 `items` 表 **id=48**（月朗路街区统筹更新，gooood）：

| 读到的字段 | 实际值 | 说明 |
|---|---|---|
| `page_title` | 月朗路街区统筹更新，杭州 / 同济原作设计工作室 | **标题抓到了** |
| `page_desc` | 160 字 | **描述抓到了** |
| `page_text` | 6523 字 | **正文整篇抓到了** |
| `cover_source` | `link` | 首图取自原文网页 |
| `status` | `pending` | 一直没变 |
| `created_at` / `updated_at` | 完全相同（2026-09-24T18:32:19.630164+08:00） | **这条记录从未被 UPDATE 过** |

埋点（`events` 表，同一会话 `sid=amjjs9bm`）：

| 时间 | 事件 | 关键属性 |
|---|---|---|
| 18:32:17.505 | `item_create_submit` | — |
| 18:32:19.826 | `ai_process_start` | `item_id=48`、`has_image=false` |
| 18:32:19.926 | `item_create_finish` | `cover_ms=1973`、`write_ms=385`、`got_meta=1` |
| — | **`ai_process_done` / `ai_process_fail` 均无** | AI 再没有回来过 |
| 18:32:19 之后 | 该 sid 无任何事件 | 用户此后没再打开任何页面 |

即：**服务端四项抓取（标题 / 描述 / 正文 / 首图）全部成功**，出问题的不是抓取，是「AI 这一步没人跑」＋「界面不显示已抓到的内容」。

### 根因

两层，第 2 层放大了第 1 层的观感：

1. **AI 任务只活在录入页的内存队列里**（`app/add.html:337` 的 `aiQueue` / `drainAi`）。
   录入 → 入库 → `enqueueAi()` 把 id 塞进**当前页面**的数组。用户点完就走，页面一关，这个数组随进程消失，而库里那条已经是 `status='pending'`。
   - 补跑只在 `app/add.html:1012` 触发，**条件是打开录入页**，且只覆盖 `recentItems(8)` 这 8 条；
   - 手动重跑入口 `retry()`（`app/add.html:677`）只接受 `status === 'failed'`，**pending 状态永远无法手动重跑**；
   - 于是形成死角：界面显示「识别中」（在跑），实际上**没有任何进程在跑**。

2. **卡面把「AI 没跑完」渲染成「这条素材没有内容」**（`app/projects/projects.js:788`、`:809`）。
   标题只取 `ai_title`（空 → 显示「未命名」），摘要取 `ai_summary || raw_text`（只填网址时 `raw_text` 为空 → 显示「（没有文字内容）」）。
   已经抓到并落库的 `page_title` / `page_desc` **在任何卡面上都不显示**，所以用户只能看到一张封面图，进而得出「只爬到了封面」的判断。

**旁证（排除「模型侧挂住」）**：用线上 SDK 在 Node 里复跑同量级负载（6000 字正文、`glm-5.3-flash`、stream+json_object），两次分别 **12.8s（首字 10.8s）** 与 **5.7s（首字 4.1s）**，均正常返回 JSON。服务端此刻正常。

### 修复

**思路：让 pending 本身就是队列。** AI 任务不再住在某个页面的内存数组里，而是记在数据库的行上；谁打开页面都能接着跑。为此给 `items` 加两列（线上 migrate + `data/schema.sql` 同步）：

| 列 | 用途 |
|---|---|
| `ai_lease_until` | 认领租约的到期时刻。认领写 `now()+150s`，跑完写 null |
| `ai_attempts` | 认领过几次，累到 3 次就不再自动重试，落 failed（"待补"），把决定权交回给人 |

两个并发问题各自的解法（二者缺一不可）：

- **重复跑** → 乐观锁。`UPDATE ... WHERE id=? AND status='pending' AND ai_lease_until IS NULL`，抢到行才算拿到执行权，返回 null 表示别处正在跑。
- **执行者死了租约没人放** → 租约带到期时间，过期谁都能接管（`lt('ai_lease_until', now)`）。这正是「用户点完就关页面」这一幕的解法。

改动的文件：

| 文件 | 改了什么 |
|---|---|
| `app/store.js` | `ITEM_COLS` / `INDEX_COLS` 带上 `ai_lease_until`；新增 `claimAi` / `stealAi` / `listPendingAi` 三个原语 |
| `app/aiqueue.js`（新） | 队列本体：领租约 → 取原件 → 调模型 → 写回 → 放租约；另含 `sweep()` 扫全表、`autoSweep()` 给普通页面用 |
| `app/add.html` | `runAi` 从 137 行缩到 25 行薄封装（原来那 137 行整体搬进 `aiqueue.js`）；启动时的补跑从「最近 8 条」改为 **sweep 全表**；新增 `_remote` 状态——本页没抢到租约时显示「正在别处识别」，不假装自己也在跑 |

| `app/projects/projects.css` | 加 `.dc-note`（"原标题 · AI 还没识别"那行） |
| `data/schema.sql` | 两列的迁移语句与注释（为什么必须有） |
| `app/_verify_home_ui.html` | 原先 5 条断言查 `add.html` 里有没有「失败落库 / 留痕」，现在这套保证搬到了 `aiqueue.js`——**断言改指向真正负责的文件**，并新增 6 条 B-001 专项断言 |

**过程中自己踩的坑（值得留着）**：第一版 `execute()` 直接复用了 `claimAi` 返回的那一行当素材用。但那次 select 只取了 `id,status,ai_lease_until,ai_attempts` 四个字段 —— 于是 `page_title / page_desc / page_text / raw_text` 全是空，模型只收到一串 URL，吐回一份**五个字段全空的 JSON**，而 `status` 照样被标成 `done`。第一次跑验证台 9 条断言就崩了这一条（而我当时刚在注释里写下"两份实现分开写的下场已经见过一次"）。修法是：调度用的精简快照一律**不**当 AI 输入，执行前重新 `fetchItem(id)` 拿全字段行。

## B-002　AI 超时被当成"模型返回了不可解析的内容"，界面因此给出一句没有原因的失败

- **严重程度**：中（不影响数据正确性，但把"慢"误报成"错"，且给用户的失败原因是空的）
- **发现时间**：2026-09-24 21:30，**补验 B-001 遗留项时发现的**（不是用户报告）
- **状态**：已修 · 已验证
- **关联**：`docs/构建记录.md` #067（待写）

### 现象

补验「超时是否真能中断」时顺手检查抛出的错误类型，发现：一次 3 秒超时的调用虽然准时中断了（3004ms 就 settle），但抛出来的错误是

```
code=undefined  name=Error  message=模型返回的不是可解析的 JSON：
```

也就是说：**超时被当成"模型坏了"处理**。落到界面上，用户看到的是 `识别失败：` 后面跟一串空白；那句专为超时写的「识别超时（封面用整图，标签留空）」永远不会出现。

### 取证

`app/_verify_ai_queue_corners.html` A 组在浏览器里跑真实调用（`timeoutMs=3000`，负载 6000 字以确保远慢于 3 秒）：

| 断言 | 结果 |
|---|---|
| 超时调用在 30s 内必然 settle（不挂住） | **在 3004ms settle**（中断本身是生效的） |
| 抛出的是 `AI_TIMEOUT` | **code=undefined / name=Error** ← 失败 |
| 报错文案可读（带真实秒数） | `模型返回的不是可解析的 JSON：` ← 失败 |

### 根因

`app/ai.js` 的 `streamOnce()` 只在 **catch 分支**里判 `timedOut`：

```js
.catch(function (e) {
  if (timedOut || (e && e.name === 'AbortError')) { /* 造 AI_TIMEOUT */ }
  throw e;
})
```

但 SDK 在 `ctrl.abort()` 之后**不一定抛 AbortError** —— 实测它把流**静默收尾**，走了 **resolve** 分支（内容是半截或空串）。于是后面的 `extractJson('')` 抛出普通的 JSON 解析错误，把超时信号盖掉了。

附带发现：同文件里 `add.html` 的失败文案把秒数写死成「超过 60 秒未返回」，而 `config.aiTimeoutMs` 早在 2026-09-22 就从 60s 提到了 90s —— **界面告诉用户的时间是假的**。

### 修复

1. `app/ai.js`：抽出 `timeoutError(timeoutMs, t0)`（两个抛点共用，避免哪天漏带 `code`）；在 **resolve 分支也补一道判据**——只要定时器到过点（`timedOut === true`），无论 SDK 用什么方式收尾都算超时。
2. `app/add.html`：失败文案与重试提示里的秒数改成按 `cfg.aiTimeoutMs` 算，不再写死。

### 验证

同一个验证台修复后重跑，**9/9 全绿**：

| 断言 | 修复前 | 修复后 |
|---|---|---|
| A2 抛出的是 `AI_TIMEOUT` | ✗ `code=undefined` | ✓ `code=AI_TIMEOUT` |
| A4 文案带真实秒数 | ✗ `模型返回的不是可解析的 JSON：` | ✓ `识别超过 3 秒未返回，已中断` |
| A1 / A3 / B1–B5 | ✓ | ✓ |

### 遗留

- 「慢」与「错」从此在数据上分开了，但**还没有任何报表去看这个比例**。
  **Elan 2026-09-24 的决定：先不做。** 触发条件写在这里，免得以后忘了为什么搁置：等你开始在意「AI 是不是变慢了」那一天再开——在那之前这个数字没有决策价值。真要做的时候，数据源已经齐了（`ai_process_fail` 带 `msg`，`ai_raw.ms` 带耗时），缺的只是一条查询和一个视图。
- 公开仓库那份**已导出但未推送**：`.git/index.lock` 上留着一个 16:41 的陈旧锁，按约定不代为处理，交给 Elan 在 GitHub Desktop 里推。
- 本机用户名 `luyu` 已随这两个既有文件进入公开仓库**并已推送**（`发布与Git交接单.md` 在 `4eed2ab`、`process-dump.py` 在 `a2276c4`）。改源文件只影响以后的导出，**历史提交里的不会消失**；要真正清除需要改写历史并强推，属不可逆操作，未做。见构建记录 #067。

## B-003　过期租约永远抢不到：写了接管函数却没接进扫描流程

- **严重程度**：高（B-001 的根治**只对一半场景生效**：执行者正常收尾时管用，执行者死了就永久卡住）
- **报告时间**：2026-09-24 22:29（Elan：上传网址后一直显示识别中，**这次他没有离开页面**）
- **状态**：已修 · 已验证 · **已发布上线（2026-09-24 22:52，Elan 本轮授权）**
- **关联**：`docs/构建记录.md` #068（待写）

### 现象

上传一个 gooood 网址后，卡片长时间停在「识别中」。这次与 B-001 不同——**用户一直停在页面上没有离开**，所以不能再用「页面关了没人接管」解释。

### 取证

出问题的是 `items` id=49（22:17:11 创建）。埋点时间线：

| 时间 | 事件 | 说明 |
|---|---|---|
| 22:17:11.949 | `ai_process_start`（`has_image=false`、`via=queue`） | **新版代码确实在跑** |
| 22:18:29 | `item_create_start` | **页面被重载**（距 start 仅 78 秒，还没到 90 秒超时，那一次 AI 调用随页面一起死了） |
| 22:19:36 | `item_create_start` | 又重载；此时租约还剩 3 秒，判定「有人在跑」→ 跳过（合理） |
| 22:28:47 | `item_create_start` | 又重载；此时租约**早已过期** → 本该接管，**却没有** |
| 之后 | 无任何 `ai_process_done` / `ai_process_fail` | 彻底死锁 |

库里 id=49 的状态：`status='pending'`、`ai_lease_until='2026-09-24T22:19:39'`（**一个过期的时间戳**）、`ai_attempts=0`、`updated_at == created_at`。

### 根因

`aiqueue.js` 的 `sweep()` 判定「租约过期 = 没有执行者」之后，调用的是 `run()` → `claim()`，而 `claimAi` 的 WHERE 条件是 **`ai_lease_until IS NULL`**。

**过期的租约是一个时间戳，不是 NULL** —— 于是它既不会被认领，也不会被接管，永久停在 pending。

我为这个场景写了 `stealAi()`（条件 `ai_lease_until < now`），**但从来没在 `sweep()` 里调用它**。两条路的 WHERE 条件互斥，缺任一条就留下一类孤儿。

**为什么 B-001 的验证台 9/9 全绿却没抓到它**：那条断言跑之前先 `clearLease()` 把租约清成了 `NULL`，恰好绕开了真实场景（真实场景是"过期的时间戳"）。测试替身把自己走通的那条路测了一遍，比不测更危险——它给出的是假的安全感。

**顺带解释「第一次为什么没跑完」**：用户在第 78 秒刷新了页面，而 AI 超时是 90 秒。调用还没到超时点就随页面一起死了，所以既没有 done 也没有 fail。这不是超时机制失灵。

### 修复

`run()` 改成**两条路依次尝试**，顺序不能反：

1. `claim()`——只认租约为 NULL 的（从未认领 / 上一个执行者正常收尾）；
2. 失败则 `steal()`——认领租约已过期的（上一个执行者死了）。

`sweep()` 的返回值加 `how: {claim, steal}` 计数，线上诊断时能一眼看出这条是正常认领的还是接管来的。

### 验证

`app/_verify_ai_recover.html` 加了断言 **④b**，并把 ④ 的前置条件从「把租约清成 NULL」改成「把租约设成**过去的时间戳**」——也就是这次真正踩到的场景。结果 **10/10 全绿**，`how={"steal":1}` 证明走的是接管路径。

**id=49 当场被救回**：`status=done`、`ai_title=潘诺恩哈尔姆树冠步道`、摘要正常、租约已释放、`ai_attempts=1`。

## B-004　网址被粘成两遍时系统默默接受，结果没有封面也没有设计总结

- **严重程度**：低-中（数据没有损坏，但一条素材静默退化成"只有标题"；且用户无从得知是自己的输入问题）
- **报告时间**：2026-09-24 22:42（Elan：上传网址后很快完成，但没有封面、没有设计说明总结）
- **状态**：已定位 · 单条数据已修复 · **防复发改进待 Elan 决定**
- **关联**：`docs/构建记录.md` #069（待写）

### 现象

上传一个 gooood 网址，这次**很快就完成了**（队列路径已通），但卡片上没有封面图，详情页里也没有「设计说明总结」。

### 取证

出问题的是 `items` id=50（22:40:39 创建）。`source_url` 是：

```
https://www.gooood.cn/yulan-xiangyuan-party-mass-service-center-...htmhttps://www.gooood.cn/yulan-xiangyuan-party-mass-service-center-...htm
```

**同一个网址首尾相接粘了两遍**，形成一个畸形 URL。连带结果：`page_title` 空、`page_desc` 0 字、`page_text` **0 字**、`cover_source='none'`、`has_thumb=false`、`ai_digest` 空。

**对照实验**（拿正确的网址直接问线上 `/api/meta`）：

| 字段 | 畸形 URL | 正确 URL |
|---|---|---|
| `page_title` | 空 | 上海浦东玉兰香苑党群服务中心 / 上海交通大学奥默默工作室 |
| `page_text` | 0 字 | **5466 字** |
| `page_desc` | 0 字 | 160 字 |
| 首图 | 无 | 有 |

**抓取链路本身是好的**，坏的只是输入。

### 根因

链条是：网址畸形 → `/api/meta` 解析不出任何东西 → 没有首图（所以没有封面）、没有正文 → `ai_digest` 为空。

**最后这一步是正确行为，不是 bug**：`ai.js` 的 `parseDigest()` 要求「理念/做法/效果」三项齐全才收，没有正文时模型给空串。**没有正文就不该编一段像模像样的假话**——这条规矩从 PRD F2-12 定下来就没变过，宁可空着也不伪造。所以"没有设计总结"是系统在诚实地报告"我没有任何材料可总结"。

值得记一笔的是：AI 仍然从那串畸形 URL 的 slug 里猜出了正确的「玉兰香苑党群服务中心」。标题没错，但封面和总结是真没了。

### 真正该改的地方（待定）

1. **录入时校验网址**：`add.html` 现在对 `fUrl` 只做 `trim()`。粘两遍这种畸形（一段字符串里出现第二个 `http`）完全可以在提交前检测出来——要么自动取第一段，要么拦下来让用户确认。
2. **抓取失败时的提示太弱**：`add.html:312` 确实有 toast「原文信息没取到（…），照常入库」，但 2.6 秒就消失，且文案强调的是"照常入库"而不是"这条会没有封面和总结"。用户看不到代价，自然不会回头检查自己粘了什么。

### 修复（单条数据）

id=50 已修好，四步缺一不可：

1. `source_url` 改回正确的一条；
2. **重新抓一次原文**（这一步最容易被漏：重跑 AI 只是跑模型，它读的是入库时抓好的 `page_*` 字段，**不会自己去抓网页**）；
3. 首图经 `/api/img` 取回字节、走管线出 400px 缩略图，与录入时完全同构；
4. 置回 `pending` 并让队列重跑一次 AI。

结果：`status=done`、正文 5489 字、`cover_source=link`、`ai_title=玉兰香苑党群服务中心`、`ai_digest` 三段齐全。
