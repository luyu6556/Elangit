**AI 的分析与决策（本次最重要的产出）**

Q-C 提出的不是一个小问题，而是这类工具的第一号死因。AI 的分析分三步：

**第一步：指出原分类里混了两个维度。**
「学校 / 住宅 / 构筑物」回答的是「对象**是什么**」；「旧建筑改造」回答的是「对它**做了什么**」。混维度的分类必然打架——一条「旧学校改造」的素材会同时像两个抽屉。**这不是命名问题，是维度问题。**

**第二步：指出「无法穷尽」是个伪问题。**
分类的职责是「把 100 条缩小到 20 条」，不是「完整描述这个世界」。用有限抽屉去覆盖无限的细分类型，方向本身就错了。因此**不该试图穷尽，不该靠命名去区分语义相近的分类**。

**第三步：给出解法——换维度，而不是改名字。**
把结构从「一级树」改成「抽屉 + 标签」两级分工：

| 层级 | 数量 | 开闭 | 归属 | 职责 |
|---|---|---|---|---|
| **抽屉**（顶层分类） | 5 个 + 1 兜底 | **封闭**，AI 无权新增 | **单归属** | 粗筛 |
| **标签** | 不限 | **开放** | **多归属** | 精确定位、交叉检索 |

`学校`、`住宅`、`公园`、`广场`、`旧建筑改造` **全部从抽屉下沉为标签**。这样一条「学校门口的口袋公园」就不会犹豫——抽屉进「城市与公共空间」，标签打「学校」「公园」。

**配套防发散机制（六条）**：单归属 / 抽屉封闭 / 抽屉粗到不重叠 / 兜底唯一且占比超 10% 即预警 / 前 30~50 条复盘 / 标签去重。

**给出可操作的判据**：「排他性测试」——给一条真实素材，3 秒内定不下放哪，这两个抽屉就该合并；连续 5 条同类都要临时判断，就该拆。**抽屉要用真实素材压出来，不是用想象力设计出来。** 因此 v0 的 5 个抽屉被明确定位为「待压测的假设」。

**对 MindMaster 大纲的三个诊断**

你原来的结构是「有意思的案例 → 学校 → 网址 → 照片 → 总结」。问题不在「简单」，而在于：

1. **树状图装不下多归属素材。** 一条素材只能待在一个枝上，多归属就得复制，复制完两份会不同步。**这就是该换成「数据库 + 标签」的根本原因。**
2. **层级里混了两个维度**（见上）。
3. **真正承载信息的只有三个字段，且缺了最有价值的那个**——「我为什么存它」。

**优化后的一条灵感结构**：原始内容（截图可多张 / 文本 / 网址，至少一项）｜来源（平台 + 链接）｜AI 摘要｜AI 画面描述｜图中文字｜抽屉（1 个）｜标签（3–5 个）｜**我的备注（为什么存、用在哪）**｜时间。

1. 要存图片 → 必须登录 → 直接推翻 PRD「不做账号体系（Q2 选 B）」
2. 就算登录了，**分享页的访客没登录 → 读不到存储里的图片 → 分享链接打开会是一片没有图的卡片流**

第 2 条更致命：它打击的正是本项目「第二重身份」（面试官当场打开链接看产出）。也就是说，**「启用账号」并不能解决访客看图的问题**。

**已提出两条路径（待用户拍板）**

| | 路径 A：图片以 base64 存数据库 | 路径 B：启用单一所有者账号 |
|---|---|---|
| 账号体系 | **不做**（维持 PRD 原样） | 做（邮箱 OTP + 密码），每个新设备登录一次 |
| 图片去向 | 全部进数据库 | 原件进存储模块，封面与缩略图仍要 base64 进库给访客看 |
| 访客能否看图 | **能**（数据库可公开读） | 只能看封面与缩略图，看不到原件 |
| 写权限边界 | 无（任何人拿到地址都能改）→ 与已接受的 R-1 同级 | 有真实边界（RLS 按所有者隔离） |
| 数据库体积 | 大（图片在内） | 小（原件不在内） |
| 改动面 | 推翻技术方案 3 章的「图片只存地址」与 2 章的存储选型 | 同左，另加账号体系 |

**AI 倾向路径 A**，理由：它不改 PRD 任何一条硬约束、不改用户习惯（无登录动作）、分享体验反而更好（访客能看到图），而它的安全降级与 R-1 已确认接受的降级是同一个级别；用例是「公开渠道收集的设计案例」，不是敏感数据。

**背景**：#012 提出的架构阻塞（平台存储模块只对已登录用户开放，与「不做账号体系 + 只读分享给外人」冲突）需要用户拍板才能继续。

**对本条回答的理解（已按此执行，如理解有误改动成本很低）**：图片统一按**长边 1600px** 归一，**保持原始宽高比、不做裁剪拉伸，长边不足 1600px 的小图不放大**。选择「长边」而不是「固定宽度」是因为素材里横图与竖图混存（小红书竖版截图很常见），按固定宽度会让竖图变得极高、体积失控；按长边归一才能让所有图的尺寸口径真正一致。此规则已写进 PRD 6.6 与技术方案 3.2。

**二、一个关键的结构决策：缩略图与原图必须分家**

图片从「文件地址」变成「内嵌 base64」之后，原来那套数据模型会出问题：如果 1600px 原图和素材字段在同一行，**列表页查 20 条卡片会顺带把几十 MB 的图拉下来**。

这不是新增的降级：R-1 当初确认接受的就是「能防普通访客误操作，防不住绕过前端直调接口」。只是现在把这件事说清楚，不再假装有服务端保护。

**把「AI 很慢」查清楚了（其中一条推翻了昨天的判断）**

4. **据此否掉一个本来打算做的方案**：把 OCR 拆成第二次独立调用。既然每次调用的成本几乎都是固定的首字延迟，拆成两次就会把等待翻倍，只换来「短输出的那次快一点」。**先量再改，避免了一次白做。**

- 重跑 AI 失败时，会把一条**本来已有好结果**的素材标成「失败」，界面出现「失败」却有摘要的矛盾状态。改为：已有结果时保留 `done`，只提示「这次重跑没成功，下面是更早那次的结果」。

- **看原图**：点卡片封面弹遮罩显示 `item_images` 里的 1600px 原件。

**两个查询设计（为 3.6 体积实测那节兜住）**

- 首页列表用 `loadIndex()`：只 SELECT 文本字段，**不带 `cover_thumb`**，按 `created_at desc` 排序。这样即使库里几百条，首屏也不至于拖下几十 MB。
- 需要缩略图时才用 `cardsByIds(ids)` 批量取（一条 `.in('id', ids)`）拿 `id / cover_thumb / cover_source / status / category`。
- `ensureCards(page)` 递归补拉：请求在飞的时候新写入的素材会漏掉，靠这一层在批次返回后再查一次补上。

**一个设计决定：AI 新造的标签单独成组**

AI 归一后可能给出标签库里没有的标签。如果侧栏只渲染 `tags` 表里的名字，这些标签就是「看不见但存在」——素材卡上有、筛选栏里没有，F4-3 会**静默漏掉**一部分内容。做法是把 `countByTag()` 里出现、但不在 `tags` 表的名字，归到侧栏一个 **「未分组（AI 新造）」** 组里，同样可点、可筛。宁可多一个组，也不要让筛选项和实际数据对不上。

**实测中发现并修掉的两个真 bug**

1. **`cover_source` NOT NULL 冲突**：走「只填文本、不传图」这条路时，代码传了 `cover_source: null`，数据库直接报 `DATABASE_23502`（非空约束）。这证明 F3-2「纯文字卡」在库里是走不通的。改为 `cover_source: c.thumb ? 'raw' : 'none'`，用一个明确的值表达「确实没有封面」，而不是用 NULL 表达。
2. **浏览器用了旧 JS**：给 `store.js` 加了 `loadIndex` 之后，页面上 `Elangit.store.loadIndex` 是 `undefined`，首页渲染出 0 张卡。原因是 `python3 -m http.server` 只发 `Last-Modified`，浏览器按启发式规则缓存了静态 JS。换成自己写的 `app/_serve.py`，强制发 `Cache-Control: no-store, must-revalidate`。**这不是产品 bug，是本地验证环境的问题，但会让人误判产品。**

### #019 ｜ 2026-09-20 ｜ 用户反馈第二轮：卡片显示项目名（新增 ai_title）+ 存量补名 + 一个窄屏 bug

**背景**

用户确认「项目名称」指 **A 案例/项目名**（不是「归属项目/合集」），并指定了卡片的信息顺序：**收藏日期挪到抽屉旁边，原来的日期位置放项目名**。本轮把这条做完，另外在验收时发现并修掉一个窄屏顶栏 bug。

**① 项目名由同一次 AI 调用给出，不额外发一次请求**

提示词里加一个 `title` 字段（专有名词、≤12 字、判不出给空字符串），跟摘要/标签/平台一起在同一次识别里返回。多开一次调用的代价是用户明确不想付的——单次识别实测 3–58s，再加一次就是双倍等待，换来的只是「名字」这一个短词。
`normalizeTitle()` 负责收口：去掉书名号与引号、压掉空白、截到 20 字（模型偶尔会带「《》」回来，截断也能兜住不听话的输出）。

**② 存量素材补名：**只写一列**，这个取舍是刻意的**

`ai_title` 是后加的字段，库里 4 条存量素材都是 NULL，卡片上会显示「未命名」。补名的做法有两条路：

| 做法 | 代价 |
|---|---|
| 整条重跑 AI，用新结果覆盖 | 重跑会**顺带给出不一样的抽屉和标签**，把用户已经理好的分类改掉——用户整理过的分类是他的劳动成果，不能被一次「补名字」冲掉 |
| 只把 AI 的 title 写进 `ai_title` | 名字没有对应的 `ai_raw` 快照可对照（F2-8 的差异基线缺一条）。**这是接受的那条** |

所以 `_backfill_title.html` **只写 `ai_title` 一个字段**，不碰 `category` / `ai_tags` / `ai_summary`，也不写 `ai_raw`——写半截快照比不写更糟：将来对照时会把「只有名字的快照」当成 AI 的完整原值。

顺带修了一个工具自身的 bug：状态判断顺序写错（把 `err` 分支嵌在 `name != null` 里），导致**失败被显示成「待补」**，错误被吞掉、看起来像在排队。判断顺序本身就会藏 bug，先判失败再判进行中再判待办。

补名结果：#1 / #5 → **Ses Clotades**，#4 → **诺邓古村盐井区更新**。三条质量都可用。

**③ 卡片信息顺序：这是宽度算术的结果，不是审美调整**

用户给的顺序（抽屉 + 日期 → 项目名 → 摘要 + 标签 → 操作条）已实装。有一处必须跟着调：**操作条从项目名那行挪到卡片最底部**。原因是 228px 宽的卡片里，项目名和「看原始截图 / 原文」两颗按钮同行时只够显示 5 个字，等于白放；改成项目名独占一行（加粗、单行省略号），按钮下沉并加 `margin-top:auto` + 上边框，卡片高度仍然整齐。

**背景**：外部复审（Codex）读完代码后交来四条意见，指明数据页的四个指标「算的不是它说的那件事」。用户转来让我执行。

| 3 | A4 只对 E7 算比例，未点开的检索不进分母 | E6 不带检索 id；自增计数器是**内存变量**，刷新归 1 | 成立 |

PRD 原文也对上了（A1 前 20 条 / A2 前 50 条 / A4 10 次检索 / A13 人工执行 + 记进构建记录）。另补一条它没提但相关的：`events` 表是 `(id, user_id, name, at, props)`，**新增事件不需要改表结构**。

**决策与理由**

1. **A4 的分母改成「发起的检索次数」，新增 E14 `search_attempt_end`。** 这是四条里唯一改**口径**而不只是改取数的。旧口径只在「点开过结果」的那些次数上算比例——**发起检索但根本没点开的次数一条都留不下**，分母被系统性做小，找回成功率被高估。而 A4 问的恰恰是「发起找回时能不能快速找到」，不是「在最终点开的那些里有多快」。现在开一笔检索就欠一笔结算，必须落到 `found`（10 秒内点开）/ `timeout`（点开了但超 10 秒）/ `abandoned`（没点开又搜了、清空筛选、离开页面）之一，**后两者都算失败**。
   - 检索 id 是**页面会话级**的，`beginSearch()` 时生成。**不能用 `sid()`**：那是设备级持久值，刷新后不变，会把不同次的检索混成一个 id。
   - `resolveSearch()` 结算后清空当前笔 → **同一次检索连点两张卡片，分母只加 1**。
   - `beginSearch()` 开新一笔时**先把上一笔结算为 `abandoned`**——用户又搜了，说明上一次没找到目标。
   - 清空筛选**仍然不记 E6**（原判断成立：那不是找东西，是放弃找），只把当前笔结算为 `abandoned`。
   - E6/E7 的语义不变、仍照记，只是都带上同一个检索 id 便于回溯；**A4 不再读它们算比例**。

2. **样本窗口由查询决定，不在渲染层补救。** A1 新增 `store.loadFirstEvents(name, limit)`（按 `at` 正序 + limit，脱离 60 天窗口）；A2 给 `diff.summary(items, opts)` 加可选 `firstN`，先取最早 N 个**有原值**的样本。`withoutRaw` 仍按全量算——否则那句「还有 N 条旧素材没有原值」会变成错的。

3. **A13 改三态。** 素材够 30 条只说明「可以复盘了」，不等于复盘做过了；数据页读不到构建记录，所以正确状态是中性显示「**待人工复盘**」，不代判达标。

4. **抽出 `app/stats.js`（复审没要求，我主动加的，已获用户同意）。** 理由不是好看，是**可测**：`stats.html` 的渲染函数是 IIFE 私有的，验证台拿不到，19/20、49/50 这类临界值只能靠肉眼看——而肉眼看不出「均值取的是最早 20 条还是最新 20 条」。门槛值现在只有一处（`GATES`），四个渲染函数不再各写 `n < 10` 这种比较。

### #024 ｜ 2026-09-20 ｜ 任务 9：发布上线（含一个发布前拦下的坑）+ 公开仓库同步

**★ 发布前拦下的坑：云服务校验请求来源（Origin），换域名就读不到库**

发布前先做了一次「同环境、只换来源」的对照实验：把**同一份发布件、同一个进程**分别用 `http://127.0.0.1:8796` 和本机局域网地址 `http://192.168.1.104:8796` 打开。

| 来源 | 结果 |
|---|---|
| `http://127.0.0.1:8796` | 正常，**3 条素材**全部渲染 |
| `http://192.168.1.104:8796` | 整页停在「加载中…」，约 20 秒后报 `读数据库失败：读素材索引失败：TypeError: Failed to fetch`；**浏览器控制台一条错都不报** |

`Failed to fetch` 是浏览器在**网络层/CORS 层**拦下请求的典型错误——请求根本没拿到可用响应。两份文件的差异只有 `config.js` 里的 `origin`，所以结论是：**云服务对请求来源做精确匹配，只有应用的保留域名被放行。**

这条如果没提前试出来，发布会的表现就是「发布成功、链接能开、但页面读不出任何数据」，而且控制台干净，极难归因。**解法的关键在 AGENTS.md 事实第 2 条**：`wbapp_az0Z1pxT1CjCvbUNffduqc` 这个应用 ID 复用才能保住保留域名与云服务校验的匹配关系——所以发布必须带 `appId`，**不能新建应用**（新应用会拿到不匹配的域名，代理过去的请求全被拦）。

**同时验掉的另一个未知数：路径式分享链接能不能活**

`_serve.py` 里的 `/s/<令牌>` → `share.html` 转发是**服务端行为**，纯静态托管做不到（PRD 4.6 选的就是路径形态）。之前只在本机验证过。发布后实测：`curl https://elangit.app.workbuddy.host/s/2zs9q7nzpcz4avg8` → **200 / 18186 B = share.html**，浏览器打开该链接显示「共 3 条素材 · 只读 / 收藏夹分享」并渲染出 3 张卡片。**平台跑的是我们自己的 Python 服务（http-service），不是静态托管，所以路径转发成立。**

不能直接发布 `app/` 目录：里面有一次性验证件（`_verify_stats.html`、`_verify_stats_ui.html`、`_verify_shots/`），验证台带「连真实库探针」按钮、截图是内部页面画面，都不该上公网。平台会把整个目录压缩上传，不做这种筛选。所以加了一步「挑出该发布的那一份」：17 个产品文件，组装到 `~/Documents/Elangit-部署/`。

### #026 ｜ 2026-09-22 ｜ 让 AI 读网页正文：摘要在卡片、设计说明总结在详情页

**背景**：用户看完首屏后提了两个问题——① 详情页「文本」卡片里那段文字到底起什么作用？② 与其让人手写，不如抓网页信息让 AI 做总结。

**第一个问题的诊断**：那张卡里的 `raw_text` 是「用户自己粘进来的原文」——只填网址的条目根本没有它（而用户的真实习惯正是**只存链接**）。所以这张卡时有时无、看不出规律，根子是**定位没写清**，不是功能缺失。诊断出来之后就自然收敛了：只在该条真有粘进来的原文时渲染。真正该补的是第二个问题。

**决策链（每一步都请用户拍过板）**

| 问题 | 选项 | 结论与理由 |
|---|---|---|
| AI 读什么 | 只读标题 + 描述 / 读网页正文 | **读正文**。一句话摘要只要判「这是什么」就够了；但要判「**值不值得点进原文**」必须知道它**怎么做、效果如何**，这些只存在于正文里 |
| 总结的公式 | 由模型自由发挥 / 固定「理念 + 做法 + 效果」 | **固定三段**。用户原话：「我的总结更像是对网页它的整体设计说明的一个总结，**如果我感兴趣我才会点进去看**」 |
| 放哪里 | 替换掉卡片摘要 / 卡片留摘要、详情页放总结 | **乙**。卡片要的是扫读（摘要管「认得」），总结只出现在已经点进来的地方（管「要不要看原文」）。**两段话不是同一件事的详略版，是两个不同的判断**，所以不做替换、只做新增 |

**正文怎么抽（`_page_meta.extract_body`）**：不引入第三方 HTML 解析库（「标准库之外零依赖」是本项目底线），四步——① 按行丢掉导航/页脚/操作位，**只匹配「动作位」特征、不做关键词粗过滤**（否则会误杀正文里正常出现的「分享」「返回」）；② 用**标签开闭配对计数**取 `article` / `main` / `div` 主体（「取第一个 `<article>` 到它的 `</article>`」这种正则在嵌套块上会截错）；③ 双语站去掉英文半篇（gooood 是中英对照排版，不去英则 token 直接翻倍、对中文总结零贡献）；④ 上限 8000 字。

送模型用 `BODY_LIMIT = 6000`：实测 4 条真实文章正文 **3,304–5,363 字**，而「效果」那一段通常写在**文章最后**——截太短会恰好把最该总结的部分截掉。

**输出为什么固定三行**：提示词写死「固定三行，每行依次以「理念：」「做法：」「效果：」开头，每行一句，整段不超过 120 字」。固定三行是为了**可扫读**——写成一段散文，用户还是会略过。`normalizeDigest()` 兜住模型不听话的形态（给成数组、三行挤成一行），**但一段没带标签的文本不会被硬塞一个标签**——那是替模型编内容。

**超时：改了时间，没有缩正文（本轮最值得记的一次判断）**

1. 现象：id=28 三次实测 33.1 / 34.0 / **67.9s**，当时阈值 60s → 第三次被掐断，落库为空。
2. 第一反应：是不是提示词变长了？于是做对照 → 长提示词与短提示词**都约 34s**。
3. 结论：回到 4.3 的老结论——**方差来自服务端排队，不来自提示词长度**。
4. 动作：`config.aiTimeoutMs` 60s → **90s**。**若当时直接去缩正文，就会为一个不存在的瓶颈丢掉「效果」段。**
5. 如实记下：这一条**未经用户拍板**（属技术参数而非需求变更，所以没停下来等），已写入技术方案 R-6 并向用户明示可推翻。

### #031 ｜ 2026-09-22 ｜ 首页搜索框铺满 + 删掉顶栏那个方块标识

**背景**：用户看首页时给了两条反馈——「搜索框在页面显示中很奇怪，也没有横向铺满」「灵感库旁边那个标识意义也没很大」。两条都不是重构需求，是**版式修正**。

**问题（先量，再改）**：

1. **搜索框为什么不铺满**：`.search` 是 `flex:1` 但带了 `max-width:420px`（旧 `style.css:222`），而同一个 `.bar` 里还有一个 `<div class="spacer"></div>`（旧 `index.html:57`）——**两个 `flex:1` 在同一行抢剩余空间**，且搜索框先被 420px 硬上限卡死。实测桌面 1440：内容区 `.bar` 1186px，搜索框只有 **420px**（232→652），右侧 768px 全空，而计数被 `.spacer` 顶到最右边 —— 视觉上就是「一个小框孤零零靠左，一个数字孤零零靠右」。手机 390 更难看：搜索框只剩 **159px** 宽。
2. **那个方块是什么**：`<a class="logo"><i></i>Elangit</a>` 里的 `<i>`，由 `style.css:39-40` 画成 16px 描边方块 + 内部实心小方块。纯装饰，无 favicon 依赖、无 JS 引用。更要紧的是 `≤460px` 那条媒体查询把 `.logo` 的文字设成 `font-size:0` —— **窄屏就只剩这个没有任何含义的方块**，这大概是「意义不大」的来源。

**决策**：

1. **搜索框选「一行铺满、计数仍在同一行」（方案 B），不选「搜索框独占一行、计数下移一行」（方案 A）**。理由：改动是 3 行（删上限 + 删两处 `.spacer`），**不动版式垂直节奏**；A 会让卡片区下移约 32px、首屏少露一点。而 placeholder 有近 50 个字，框宽一点反而更好读；且 1188px 与 1090px 的输入框在观感上没有实质差别，不值得为「多 100px」换一次版式位移。
2. **方块删掉，窄屏改成整块收起**（不是「保留方块只修窄屏」）。理由：单用户私人工具，顶栏标识的识别价值接近零；一个既不像 logo 也不像图标的方块，更像是没渲染完。
3. **界面稿同步**（用户明确要求）：`docs/05-界面稿.html` 里同一行 `max-width:420px` 与同一段 `.logo i` 规则一起改掉。
