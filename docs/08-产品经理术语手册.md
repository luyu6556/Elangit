# 产品经理全流程与核心术语手册 v1

> 适用对象：建筑专业转岗、零产品实习经验、1 个月冲刺中小厂产品实习
> 使用说明：这是第 1 周的打底材料。术语只收面试和实际工作里真会碰到的，不堆砌。
> 主线：需求规划 → PRD 撰写 → 设计研发评审 → 研发跟进 → 测试验收 → 上线复盘

---

## 一、先把三个误解拆掉

### 误解 1：产品经理是"想点子的"

不是。点子不值钱，值钱的是**判断哪个点子值得做、为什么现在做、做完怎么验证**。PM 的核心产出是判断，不是创意。

### 误解 2：产品经理是"小老板"，指挥开发和设计

PM 对研发、设计**没有直接管辖权**（他们不向 PM 汇报）。PM 靠两样东西推事情：把问题和价值说清楚让人愿意做；把优先级排明白让人知道为什么先做这个。所以 PM 的硬技能里，"说清楚"和"让各方达成一致"占了大半。

### 误解 3：产品经理就是画原型、写文档

原型和文档是**沟通工具**，不是目的。写 PRD 的真正目的不是产出一份文档，而是**逼自己把逻辑想完整，然后让开发、设计、测试对同一件事形成同一幅画面**。文档写得漂亮但逻辑有洞，等于没写。

---

## 二、PM 到底对什么负责

一句话：**对一个产品在"做不做、做成什么样、做完有没有用"这三件事上的判断质量负责。**

| 三个问题 | 对应能力 | 失败的样子 |
|---|---|---|
| 做不做 | 需求判断、优先级 | 做了一堆没人用的功能 |
| 做成什么样 | 方案设计、逻辑闭环 | 上线后被吐槽"这什么玩意" |
| 做完有没有用 | 数据度量、复盘 | 说不清自己做的东西带来什么 |

### PM 的四个角色

1. **用户代言人** —— 在会议室里替不在场的用户说话。"用户会怎么用""这么改用户会懵"。
2. **业务翻译官** —— 把业务方模糊的诉求（"我想要个能管库存的东西"）翻译成研发能落地的明确需求。
3. **项目推动者** —— 不是管人，是管依赖、管阻塞、管信息同步。谁卡住了、谁在等谁、风险在哪。
4. **结果 Owner** —— 上线后数据是涨是跌，第一个被问的是 PM。

## 三、六阶段全流程（主干）

| 阶段 | 要解决的问题 | PM 的核心动作 | 主要交付物 | 主要协作对象 |
|---|---|---|---|---|
| 1 需求规划 | 到底该做什么 | 收集需求、判断价值、排优先级 | 需求池、优先级结论 | 业务方、用户、老板 |
| 2 PRD 撰写 | 具体做成什么样 | 拆解逻辑、写规则、画原型 | PRD、原型 | 设计、研发 |
| 3 设计研发评审 | 这么做行不行、谁来做、多久 | 讲清背景逻辑、对齐方案、确认排期 | 评审结论、排期表 | 设计、研发、测试 |
| 4 研发跟进 | 会不会按时按质做出来 | 拆解任务、跟进度、处理变更和风险 | 任务拆解、风险清单 | 研发、测试 |
| 5 测试验收 | 做出来的是不是当初说好的 | 写验收标准、过测试用例、判断 Bug 优先级 | 验收清单、Bug 列表 | 测试、研发 |
| 6 上线复盘 | 做完有用吗、下次怎么做得更好 | 定指标、看数据、写复盘 | 复盘报告、数据观察清单 | 数据、运营、全员 |

### 阶段 1：需求规划

**这一阶段在解决什么**：在一堆"想做的事"里，挑出**现在最该做的那件**，并说清楚为什么。

**核心术语**

| 术语 | 解释 |
|---|---|
| 需求池（Backlog） | 所有收集到的、待评估的需求集合。不是待办清单，是**待评估**清单。 |
| BRD / MRD / PRD | 商业需求文档（讲为什么做、商业价值）/ 市场需求文档（讲市场、竞品、用户）/ 产品需求文档（讲具体做成什么样）。实际工作中 MRD 用得越来越少，PRD 是 PM 的看家活。 |
| 用户故事（User Story） | 标准句式：作为一个**[角色]**，我想要**[做什么]**，以便**[获得什么价值]**。第三句（价值）最容易被漏，也最重要。 |
| MVP | Minimum Viable Product，最小可用产品。用最小成本验证核心假设，不是"简陋版"。 |
| KANO 模型 | 把需求分五类：必备（没有会骂）、期望（越多越满意）、魅力（没有不怪你，有就惊喜）、无差异（做不做无所谓）、反向（做了反而烦）。 |
| RICE 评分 | 优先级打分：Reach（覆盖人数）× Impact（影响程度）× Confidence（信心）÷ Effort（投入成本）。 |
| MoSCoW | Must / Should / Could / Won't 四档分级，简单粗暴但好用。 |
| 伪需求 | 用户嘴上说的解决方案，不是他真正的目标。用户说"我想要一匹更快的马"，真实需求是"更快到达"。 |
| 范围蔓延（Scope Creep） | 做着做着需求越加越多，最后工期失控。PM 的核心职责之一就是守住范围。 |

**PM 的具体动作**
1. 收集：用户反馈、业务方诉求、老板想法、竞品动态、数据异常，全部进池。
2. 溯源：每个需求追问"这个需求背后，谁、在什么场景、遇到什么问题"。追不到问题的需求，多半是伪需求。
3. 判断：用 KANO / RICE 之类的框架给需求定级（框架只是让判断可解释，不是替你判断）。
4. 排期：跟老板和业务方对齐优先级，明确这一版做什么、**不做什么**。

**常见坑**
- 把用户原话当需求直接做（伪需求陷阱）。
- 只说"要做"，不说"为什么现在做"。
- 不好意思砍需求，导致全做的是低价值的。

**面试常问**
- "你怎么判断一个需求该不该做？"
- "需求太多排不下，你怎么排优先级？"
- "遇到业务方坚持要做但你觉得没价值的需求，怎么办？"

### 阶段 2：PRD 撰写

**这一阶段在解决什么**：把"要做个什么东西"变成**研发和测试能照着干活、且不会产生歧义**的说明。

**核心术语**

| 术语 | 解释 |
|---|---|
| PRD | Product Requirements Document，产品需求文档。 |
| 交互稿 / 原型 | 页面长什么样、怎么跳转的工具（Axure、Figma、墨刀）。低保真（线框图）看结构，高保真看视觉。 |
| 正常流程 / 异常流程 | 正常流程是用户顺利走完的路径；异常流程是网络失败、输入非法、权限不足、数据为空等。新手 PRD 最大的洞在异常流程。 |
| 边界条件 | 极限值：字数上限、数量上限、并发上限、时间边界。不写清楚，开发就自己猜，然后出 Bug。 |
| 状态机 | 一个对象从生到死经过哪些状态、谁能触发流转。B 端必备（如：工单的 待受理→处理中→已解决→已关闭）。 |
| 字段说明 | 每个字段的名称、类型、是否必填、默认值、校验规则、数据来源。 |
| 埋点 | 在页面上采集用户行为的数据点（谁、在什么时间、点了什么）。**上线前必须提埋点需求，上线后补不上历史数据。** |
| EARS 需求写法 | 一种让需求无歧义的句式规范： ubiquitous（系统始终...）、event-driven（当[事件]时，系统应...）、unwanted（若[异常]，则系统应...）、state-driven（在[状态]下，系统应...）、optional（若[特性]，则系统应...）。 |

**PM 的具体动作**
1. 画用户路径：用户从哪进来、经过几步、在哪离开。
2. 写功能清单和规则：每条规则要能验证（"加载要快"不是规则，"首屏 2 秒内渲染完成"才是）。
3. 画原型：不用好看，但状态和跳转要全。
4. 补齐异常和边界：这是区分新手和老手的地方。
5. 写埋点方案：这个版本要观察哪些数据。

**常见坑**
- 只画了"阳光路径"，异常全没写，开发来一个问题问一次。
- 规则写"友好提示""合理排序"这种无法验证的词。
- 忘了写埋点，上线后没法验证效果。

**面试常问**
- "一份好的 PRD 应该包含什么？"
- "你写的 PRD 被开发说实现不了，怎么办？"

### 阶段 3：设计研发评审

**这一阶段在解决什么**：在动手写代码之前，**让所有人理解一致，并把方案的技术可行性、工期、风险摆到桌面上**。

**核心术语**

| 术语 | 解释 |
|---|---|
| 评审 | 需求评审（讲清做什么、为什么）/ 设计评审（交互视觉是否可行）/ 技术方案评审（研发讲怎么做）。 |
| 交互设计师 / UI 设计师 | 交互（UE/UX）管流程和信息架构；UI 管视觉呈现。小公司可能一个人全包。 |
| 技术可行性 | 这个需求技术上做得到吗？代价多大？有时 PM 的方案技术上能做但成本极高，需要换方案。 |
| 排期 | 研发估工时、定上线时间点。PM 负责在需求价值和工期之间做取舍。 |
| 里程碑 | 关键时间节点：提测日、联调日、灰度日、上线日。 |

**PM 的具体动作**
1. 讲背景先于讲方案：先说解决什么问题、给谁用，再说做成什么样。跳过背景直接讲方案，评审必被挑战。
2. 记录评审结论：哪些通过、哪些要改、谁负责、什么时候定。
3. 拉齐排期：跟研发确认工时，跟老板确认优先级，冲突时砍需求不砍质量。

**常见坑**
- 只顾讲方案，不交代背景，导致评审变成挑战会。
- 评审没有书面结论，事后各说各话。

---

### 阶段 4：研发跟进

**这一阶段在解决什么**：**让事情按约定推进，风险在变成事故之前被发现。**

**核心术语**

| 术语 | 解释 |
|---|---|
| 迭代（Sprint） | 一个固定长度的开发周期，Scrum 里常见 2 周（一般 1–4 周）。 |
| 站会（Standup） | 每天短会，同步"昨天做了什么、今天做什么、有什么阻塞"。 |
| 联调 | 前端和后端把各自的部分接起来跑通。 |
| 阻塞 / 依赖 | A 做不了因为在等 B。PM 的价值就是盯这些依赖。 |
| 技术债务 | 为了赶进度写的临时方案，早晚要还。PM 要知道债在哪、什么时候还。 |
| 需求变更 | 中途改需求。不是不能改，但必须走流程：评估影响 → 同步各方 → 重新排期。 |

**PM 的具体动作**
1. 把需求拆成研发任务，确认每个任务的责任人和时间点。
2. 每天看进度，重点不是催，是**问"有没有卡住"**。
3. 变更管理：任何变更先评估对工期和其他需求的影响，再决定。
4. 维护风险清单：哪条有风险、影响多大、预案是什么。

**常见坑**
- 把所有阻塞都自己扛，不升级。该找老板协调就找。
- 口头答应变更，不评估影响，最后全队背锅。

---

### 阶段 5：测试验收

**这一阶段在解决什么**：**确认做出来的东西就是当初说好的那个，且不会把线上搞崩。**

**核心术语**

| 术语 | 解释 |
|---|---|
| 测试用例 | 一组"前置条件 + 操作步骤 + 预期结果"。PM 至少要把核心路径的用例自己过一遍。 |
| 冒烟测试 | 先跑最核心的功能，挂了就直接打回，不浪费时间细测。 |
| 回归测试 | 改了 A，要确认 B、C 没被改坏。 |
| 提测 | 研发说"做完了，可以测了"。 |
| Bug 优先级 | 通常 P0 阻断（线上崩了）/ P1 严重（核心流程走不通）/ P2 一般 / P3 体验优化。PM 要判断哪些**必须修完才能上线**。 |
| 灰度发布 / 全量 | 先放给一小部分用户（如 5%），观察没问题再全量。 |
| 回滚 | 上线出问题，退回上一个版本。 |

**PM 的具体动作**
1. 上线前自己走一遍主流程（**PM 亲自验收，不能只看测试报告**）。
2. 判断 Bug 是否阻断上线：核心流程走不通=阻断；边角体验问题=可延到下个迭代。
3. 确认埋点已生效，否则上线后没有数据。

**常见坑**
- 只验收"正常路径"，异常和兼容性没测。
- 上线了才发现埋点没加，这一版的数据永远拿不到。

### 阶段 6：上线复盘

**这一阶段在解决什么**：**做完有没有用？下次怎么做得更好？** 不复盘的团队会在同一个坑里摔第二次。

**核心术语**

| 术语 | 解释 |
|---|---|
| 北极星指标 | 一个最能代表产品核心价值、能指导全团队取舍的指标。 |
| OSM 模型 | Objective（目标）→ Strategy（策略）→ Measure（度量），把目标拆到可衡量的指标。 |
| AARRR | 获取 → 激活 → 留存 → 收入 → 推荐，经典用户生命周期漏斗。 |
| A/B 测试 | 同一时间给不同用户看不同方案，用数据决定哪个更好。**必须有对照组**。 |
| 基线数据 | 改之前的数据。没有基线，就无法判断改完之后是涨了还是跌了。 |
| 复盘 | 不是总结会，是回答四个问题：预期是什么、实际是什么、差在哪、下次改什么。 |

**PM 的具体动作**
1. 上线前就定好：这次要观察哪几个指标（上线后补定=耍流氓）。
2. 观察一个完整周期（至少一周，看留存而不是只看首日）。
3. 写复盘：目标达成情况、意外发现、遗留问题、下一版候选需求。

**常见坑**
- 上线即结束，不看数据不复盘。
- 只看总量不看留存，被首日推广数据骗了。

## 四、高频术语速查

### 用户与需求
| 术语 | 解释 |
|---|---|
| Persona 用户画像 | 基于调研虚构的典型用户模型，帮团队形成共识。 |
| 用户旅程地图 | 用户从接触产品到达成目标的完整路径 + 每个节点的情绪和痛点。 |
| 痛点 / 爽点 / 痒点 | 恐惧/麻烦 / 即时满足 / 理想中的自己。 |
| 可用性测试 | 让真实用户试着用，你在旁边看他在哪卡住。 |
| Edge Case 边缘场景 | 极少数但必须处理的场景（如同时提交、网络中断、超长文本）。 |

### 数据
| 术语 | 解释 |
|---|---|
| DAU / WAU / MAU | 日 / 周 / 月活跃用户数。 |
| 留存率 | 第 N 天还回来的用户占比。次日、7 日、30 日留存是最常看的。 |
| PV / UV | 页面浏览量 / 独立访客数。 |
| 转化率 | 完成目标动作的用户 ÷ 进入流程的用户。 |
| 漏斗 | 多步流程里每一步的流失，用来定位"人是在哪一步跑掉的"。 |
| GMV | 成交总额（电商）。 |
| ARPU | 每用户平均收入。 |
| LTV / CAC | 用户生命周期价值 / 获客成本。**LTV > CAC 生意才成立**。 |
| 北极星指标 | 见阶段 6。 |

### B 端特有（你的作品集方向，重点记）
| 术语 | 解释 |
|---|---|
| SaaS | 软件即服务，按年订阅付费的云端软件。 |
| 续费率 | 到期继续付费的客户比例。B 端的生死线。 |
| ACV | Annual Contract Value，年度合同金额。 |
| 多租户 | 一套系统服务多家企业，数据互相隔离。 |
| RBAC | 基于角色的权限控制：先定义角色（如施工员/项目经理），再给角色配权限。 |
| 工作流 / 审批流 | 一个任务在不同角色之间怎么流转、谁审批。B 端产品的核心。 |
| SLA | 服务等级协议，承诺的可用性和响应时长。 |
| 私有化部署 | 装在客户自己的服务器里，不放在云端。 |
| 决策链 | 一个 B 端采购通常涉及：决策人（掏钱）、把关人（技术/合规审核）、使用方（真正用的人）、影响者。PM 要同时满足这几拨人。 |
| 客户成功 | 帮客户把产品用起来、用出价值，从而提高续费率。 |

### 研发与项目
| 术语 | 解释 |
|---|---|
| 前端 / 后端 / 客户端 | 用户看得见的界面 / 服务器和数据库逻辑 / 手机 App（iOS、Android）。 |
| API / 接口 | 前后端之间传递数据的约定。 |
| 埋点 | 见阶段 2。 |
| QA | 测试工程师。 |
| 技术债务 | 见阶段 4。 |
| 阻塞 | 见阶段 4。 |

## 五、互联网黑话：认识即可，面试慎用

下面这些你听懂就行，**面试时不要主动堆**，用多了会被认为"只会说不会做"。

| 黑话 | 实际意思 |
|---|---|
| 对齐 | 让几方达成共识 |
| 拉通 | 把跨部门的信息串起来 |
| 闭环 | 事情有始有终，有结果有反馈 |
| 抓手 | 切入点 |
| 颗粒度 | 细节的粗细程度 |
| 打法 | 做事的策略 |
| 底层逻辑 | 事情的根本原因 |
| 组合拳 | 几个手段一起上 |
| 护城河 | 别人抄不走的竞争优势 |

**判断标准**：能用大白话说清楚的事，就用大白话。面试里"我用 RICE 给需求排了优先级"比"我拉通各方对齐了颗粒度"有说服力得多。

## 六、C 端 PM 与 B 端 PM 的真实差别

| | C 端 PM | B 端 PM |
|---|---|---|
| 一天里最多的时间 | 看数据、开增长实验会、跟设计师磨体验 | 跟业务方聊流程、画状态机和权限表 |
| 需求从哪来 | 用户反馈、数据分析、竞品 | 客户/销售/实施团队、行业规范 |
| 决策依据 | 数据指标（留存、转化） | 业务是否真的跑通、客户是否续费 |
| 最难的地方 | 众口难调，且用户会用脚投票 | 不懂业务就做不出东西，且业务很枯燥 |
| 新人优势 | 上手快、易共情 | 有行业背景=直接加分 |

**对你的意义**：建筑背景在 B 端是**真加分**，因为你懂一个行业的真实工作方式。这是别人短期学不来的。

## 七、建筑 → 产品 术语对照（你的翻译器）

面试时把经历讲成"产品语言"，用这张表：

| 建筑语境 | 产品语境 |
|---|---|
| 设计任务书、甲方诉求 | 需求背景、需求池 |
| 场地条件、规范红线 | 业务约束、技术约束 |
| 使用者行为流线分析 | 用户路径、用户故事 |
| 方案设计 / 扩初 / 施工图 | 原型 / 交互稿 / PRD |
| 结构、机电专业交底 | 设计研发评审 |
| 现场配合、设计变更 | 研发跟进、需求变更管理 |
| 竣工验收 | 测试验收 |
| 使用后评估（POE） | 上线复盘、数据观察 |
| 建筑面积、造价、规范三重约束 | 资源约束下的优先级取舍 |
| 多专业协调 | 跨职能协作推动 |
