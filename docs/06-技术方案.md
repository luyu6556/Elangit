## 1. 架构总览

```
   手机浏览器 ──┐
                ├──→ 线上网页（单页应用，响应式）
   电脑浏览器 ──┤            │
                │            ├─ 数据库：素材 / 抽屉 / 标签 / 分组 / 设置
   分享链接访客 ─┘            ├─ 文件存储：截图与上传图片
                              └─ 大模型：摘要 · 画面描述 · 图中文字 · 标签 · 分类
```

**一句话**：一个部署在云端的响应式网页应用，数据与 AI 能力全部使用 WorkBuddy 云服务，用户不需要买服务器、不需要域名、不需要自备 API Key。

**明确不搭的东西**：不做自建后端服务，不做用户注册登录体系，不做原生 App。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 单文件 HTML + 原生 JS + 内联 CSS，无构建步骤 | 项目规模小（4 个页面）；无构建负担意味着你以后想改文案不用装环境。**实测前提是包体控制在单文件可维护范围内**，若后期代码超过 ~2000 行再考虑引入构建 |
| 存储 | 云服务 **Database** 模块 | 跨设备同步与分享的前提（PRD Q-A 已确认必须上云） |
| 图片 | **不使用云服务 Storage 模块**；图片统一转 1600px 后以 base64 存入数据库 `item_images` 表 | **2026-09-20 修订**。实测平台 Storage 只对已登录用户开放（连读都要登录），未登录访客读不到图；而 `Auth` 又明确不支持匿名登录。改用数据库后，未登录访客也能看到图片，这与「不做账号体系 + 只读分享给外人」两条是兼容的。代价与体积实测见 3.6 |
| AI | 云服务 **LLM API** 模块（免密钥） | PRD Q-H 已确认先用平台自带能力。**多模态已验证通过**（见 4.2） |
| 账号 | **完全不启用**云服务 Auth 模块 | PRD 不做账号体系。所有者保护退化为纯前端口令（见第 6 章） |
| 部署 | 发布为在线应用，复用同一应用 ID | 应用 ID 复用才能保住域名与云服务校验的匹配关系 |

**SDK 引入方式**：项目是纯 HTML、无构建步骤，按规范走 **CDN 引入**（不使用 npm 安装），初始化时同时传入 `endpoint` 与 `publishableKey` 两个公开配置值。这两个值在激活云服务后由平台返回，**不写死在代码里**。

## 3. 数据表设计

**2026-09-20 修订**：图片从 Storage 改为 base64 存入数据库，表数由 5 张变为 **6 张**。本节的表结构**已实际建成并验证通过**（状态见 3.7）。

### 3.1 items（素材，主表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 自增整数 | 主键 |
| user_id | 字符串 | **固定值 `local-owner`，预留**。为将来接账号体系留的接口，第一版不参与筛选 |
| source_type | 字符串 | `text` / `image` / `mixed` |
| raw_text | 文本 | 粘贴的原文 |
| source_platform | 字符串 | 小红书 / 公众号 / 网页 / 其他 |
| source_url | 字符串 | 原文链接 |
| ai_summary | 文本 | AI 摘要 |
| **ai_title** | 文本 | **案例/项目名**，卡片与详情页首个可见字段（任务 6 补，见下） |
| ai_caption | 文本 | AI 画面描述 |
| ocr_text | 文本 | AI 提取的图中文字 |
| ai_tags | 数组 | AI 生成的标签名列表 |
| my_tags | 数组 | 用户手动加的标签名列表 |
| category | 字符串 | 抽屉名（**必须来自 categories，AI 无权新建**） |
| **cover_thumb** | 文本 | **卡片缩略图（base64）**。长边 400px / JPEG q72，列表页只取这个字段 |
| **cover_source** | 字符串 | 封面来源：`crop`（按 AI 矩形裁取）/ `raw`（整图未裁）/ `none`（这条没有图）。**取值与代码一致，本行 2026-09-20 订正**：原写 `manual`，但 v1 不做手动框选（F5-8 只做「换回原图」「按 AI 矩形重裁」「换哪张图当封面」三件事），所以没有 `manual` 这个值 |
| **cover_index** | 数字 | 封面取自第几张原图 |
| my_note | 文本 | 我为什么存它 |
| **ai_raw** | JSON | **AI 最近一次成功识别的原值快照**（任务 6 新增，见下） |
| created_at / updated_at | 时间戳 | |
| status | 字符串 | `pending` / `done` / `failed` |
| share_token | 字符串 | 单条分享令牌，空表示未分享 |

**为什么单开 ai_raw 存一份 AI 原值（2026-09-20 · 任务 6）**：`ai_summary`／`category`／`source_platform` 这些字段是「用户当前看到的值」，用户一改，AI 原来给什么就永远查不到了。但有两处非要不可：

- **F5-6** 要求把 AI 原先的平台猜测**以黄色虚线框留在选项上供对照**——不存原值就画不出来；
- **F2-8** 要求记录「AI 原值 → 用户改动」的差异——没有基线就算不出差异。

所以 AI 说什么原样留一份，用户编辑概不触碰。内容是 `{category, categoryCorrected, categoryOutOfList, tags, summary, caption, ocrText, platform, rect, ms, at}`。

语义定为「**AI 最近一次成功的输出**」，重跑会覆盖：重跑是用户主动触发的一次重新识别，差异基线理应跟着移动，否则「我改了多少」会越算越离谱。

存量数据（本列上线前写入的素材）这一列是 NULL。界面据此**如实说明**「这条早于「记录 AI 原值」上线，矩形没留下来」，而不是顺口断言「AI 没给矩形」——后者是在断言一个查不到的事实。

**为什么加 ai_title（2026-09-20 · 任务 6 收尾）**：卡片上原本只有「摘要」，「这张图是什么案例」要读完整句摘要才知道。摘要 ≤50 字、AI 又写得偏描述性（「废弃高架货运铁路改造为城市空中公园」），扫一眼认不出是哪条素材。项目名是专有名词（「纽约高线公园」「诺邓古村盐井区更新」），辨识度远高于摘要。

- 由 AI 在**同一次调用**里一起给（提示词加 `title` 字段，≤12 字，判不出给空串），不额外增加一次请求；`normalizeTitle()` 去掉书名号/引号/空白并截到 20 字。
- 空串与 NULL 在界面上都显示「未命名」，但**语义不同**：空串是「AI 看了但判不出」，NULL 是「这条写在这个字段存在之前」。界面区分对待。
- 存量素材补名走的是**一次性工具** `app/_backfill_title.html`（补完已删除），它**只写 `ai_title`**：重跑 AI 会顺带给出不一样的抽屉和标签，那会把用户已经理好的分类改掉；也不写 `ai_raw`，避免造出一个「只有名字」的半截快照。代价是这几条补出来的名字**没有对应的 AI 原值可对照**——这是有意选的取舍。

**为什么缩略图单独放在 items 上，而不是和原图放一起**：列表页要一次取 20 条卡片。若缩略图与 1600px 原图同表，一次列表查询就会把几十 MB 图片拉下来。把 400px 缩略图做成 items 的一个字段后，列表查询是单表且只取这张小图（实测 20 张卡约 0.5MB），原图留给详情页按需取。

**标签为什么存「名字」而不是「ID」**：标签是开放集合，允许随时新增。存名字让「AI 生成一个新标签」不需要先建记录再引用，少一次写入；代价是改名要批量更新。考虑到标签总量在几百量级，这个代价可接受。

### 3.2 item_images（图片，新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 自增整数 | 主键 |
| item_id | 外键 | 指向 items，级联删除 |
| seq | 数字 | 同一素材内第几张（0 起）；与 item_id 组成唯一约束 |
| mime | 字符串 | 统一 `image/jpeg` |
| width / height | 数字 | 像素尺寸 |
| byte_size | 数字 | 原始字节数（不含 base64 膨胀） |
| **data_base64** | 文本 | 图片本体，base64 编码 |
| **ai_rect** | JSON | **这一张图**被 AI 判出的主体矩形 `{top,right,bottom,left}`（百分比）。任务 8 新增 |
| created_at | 时间戳 | |

**为什么矩形要按图存一份**（2026-09-20，任务 8）：`items.ai_raw.rect` 是「**送进模型那张图**」的矩形。一旦用户在详情页把封面换成第 2 张图，`ai_raw.rect` 就对不上新图了——A14 的「重裁」当时因此失效（详情页判断条件是 `rect && cover_index===0`，换了图就永远不成立）。改成按 `(item_id, seq)` 存，重裁对任意一张封面图都成立（F5-8 第三条兜底）。

**图片统一规格（2026-09-20 决定）**：**长边统一 1600px、保持原始宽高比、不放大小图**，JPEG q88。长边不足 1600px 的图保持原尺寸——放大只增加体积、不增加信息。

### 3.5 tags（标签）与 settings（设置）

- **`tags`**：`id`、`user_id`、`name`（唯一）、`group_id`（外键）、`created_at`。已预置 **32 个起始标签**（取自 PRD 4.5 与界面稿演示数据），供 AI 优先复用。

- **`settings`**：单条记录（`id` 恒为 1，带 CHECK 约束）、`share_enabled`、`share_token`（收藏夹分享令牌）、`updated_at`。
  **修订**：原方案里的 `owner_passcode_hash` **已移除**。原因见第 6 章——在路径 A 下口令只是前端门禁，把哈希存进一个匿名可读可写的库，既不提供安全，又制造「看起来有保护」的错觉。

| 项目 | 实测值 |

### 3.8 events（埋点，任务 8 新增，第 7 张表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 自增整数 | 主键 |
| user_id | 文本 | 恒为 `local-owner`（不做账号体系，没有第二个写入者） |
| name | 文本 | 事件名，见 PRD 第 9 章（`item_create_start` 等） |
| at | 时间戳 | 事件发生时刻，默认 `now()` |
| props | JSON | 事件自带字段（耗时、关键词、素材 id、设备…） |
| created_at | 时间戳 | |

索引 `events(at desc)`。RLS 同其余各表（`anon, authenticated` + `FOR ALL USING(true)`），因为未登录状态下访客也可能触发读；**写操作在 `store.js` 的 `insertEvent()` 里过 `guard()`**——也就是说这一层的门是前端门，和其余写入口一致。

**为什么不给 E1~E13 全部建事件**（这是任务 8 唯一一个真正的设计决定）：

判断标准只有一条——**这件事能不能从库里的当前状态算出来**。

| 事件 | 能不能派生 | 处理 |
|---|---|---|
| E4 改了哪些 AI 字段 | 能：`items.ai_raw` 对比现值，就是 F2-8 的差异 | **不写事件**，用时现算（`diff.js`） |
| E11 落进兜底抽屉 | 能：`category` 等于兜底抽屉名 | **不写事件**，现算 |
| E12 手动更正来源平台 | 能：`ai_raw.platform` 对比 `source_platform` | **不写事件**，现算 |
| E1/E2/E3/E5 耗时 | 不能：过程量，状态里留不下痕迹 | 写事件 |
| E6/E7/E8 搜索行为 | 不能：同上 | 写事件 |
| E9 会话 | 不能：同上 | 写事件 |
| E13 换封面 | 不能：换完只剩结果，看不出「是谁换的、为什么换」 | 写事件 |
| E10 访客访问分享 | 能，但**不做** | 见 9.8 第 3 条 |

结论：**13 条里实际写 9 条**。少写一处就少一处会漂移的副本——改两次的话，事件流还得靠顺序才能拼出「现在的差异」，而直接对比永远不会不一致。

## 4. AI 调用设计

**一次调用完成四件事**：输入原始内容（文本 + 图片），输出结构化 JSON：摘要、画面描述、图中文字、抽屉、标签。

### 4.1 关键设计点

| 点 | 做法 | 为什么 |
|---|---|---|
| **抽屉必须封闭** | 把当前抽屉清单作为**枚举**写进提示词，并要求只能从中选一个 | 这是 PRD F2-6 的硬约束，也是防止「素材越积越乱」的核心机制 |
| **标签必须参考已有标签库** | 把现有标签名一并给模型，要求「优先复用，确实不匹配才新建」 | 直接针对标签发散的失败模式 |
| **失败不能丢素材** | 先写入素材（状态 `pending`），再调 AI，成功后更新为 `done`。AI 挂了素材仍在 | PRD F2-7 |
| **结果必须可改** | AI 结果作为**默认值**回填，不是最终值 | 录入摩擦预算里已算进「确认 3 秒」 |
| **记录改动差异** | 用户改动时保存「AI 原值 / 用户改后值」 | 埋点 E4，唯一能量化 AI 标签可用率的办法 |

### 4.2 【已验证 · 2026-09-20】

**云服务的 LLM 模块支持图片输入（多模态）——已在真实调用中验证通过。**

验证方式：单文件验证页，用 `auto` 模型 + 一条真实小红书截图（1266×860，739KB → base64 986KB，以 data URL 直接传入）。

| 验证项 | 结果 |
|---|---|
| 模型目录是否声明支持 | 30 个模型中 **19 个显式声明 `supportsImages: true`**（含默认 `auto`）；10 个显式 `false`；1 个未声明（`hunyuan-image-v3.0`，不选它） |
| 真实调用是否成功 | 成功。`finish_reason=stop`，耗时 26.0s（其中思考链 675 tokens），首 chunk 4.6s |
| 图片是否真被看到 | 是。OCR 把截图里的标题、设计单位、室内面积、话题标签、发布日期全部正确提取 |
| 抽屉判断是否正确 | 是。判为「建筑与构筑物」，标签 `住宅 / 别墅 / 案例借鉴 / 海景住宅 / 极简建筑` |
| 来源平台预判 | 正确判为「小红书」 |
| 是否必须先把图片上传拿到公网 URL | **不必须**。base64 data URL 可直接传入 |

**结论**：走原路径，不启用降级路径。F2 的四件事（摘要 / 画面描述 / 图中文字 / 抽屉+标签）再由真实模型承担已无障碍。

**选型建议**：默认用 `auto`（平台自动匹配）。若关心成本，可选 `glm-5.3-flash`（x0.06）或 `deepseek-v4.1-flash`（x0.03，原生多模态）——本次调用 `auto` 消耗 0.76 credits。成本差异需在真实使用中观察，暂无依据断言哪个够用。

### 4.3 【实测 · 2026-09-20】AI 调用耗时封不住长尾

样本：5 张真实素材，模型 `glm-5.3-flash`，送模型的图压到长边 1000px。三轮独立采样，单位秒：

| 素材 | 轮次 1 | 轮次 2 | 轮次 3 |
|---|---|---|---|
| Ses Clotades（小红书截图 1266×860） | 5.8 | 16.6 | 15.5 |
| 纽约高线公园（1741×1011） | 11.4 | 6.7 | 8.2 |
| 2025 阿卡汗建筑奖（网页头图 700×449） | 10.5 | 11.2 | 41.7 |
| 衡水垂直农场（网页头图 700×449） | 3.7 | 3.2 | 3.9 |
| Ghaf Woods 体验中心（网页头图 700×449） | 3.5 | 4.4 | 3.7 |

**同一张图三次调用可以差 4 倍**（阿卡汗 10.5 → 41.7s）。所以 PRD F1-4 的「≤10s」不能当作 AI 识别步骤的硬指标（已按 R-5 改写）。

#### 时间花在哪里：首字延迟

对单次调用做了分段计时，结论明确——**耗时几乎全在「第一个字什么时候到」**：

| 指标 | 值 |
|---|---|
| 总耗时 | 57.8s |
| **首字延迟** | **51.2s** |
| 输出长度 | 996 字符 |
| 送模型的图 | 116KB / 1000×581 |
| 提示词 | 1160 字符 |

图片大小（全样本 62–178KB）与输出长度都不是瓶颈，**排队与预填充才是**。

由此**否掉一个看起来合理的方案**：把 OCR 拆成第二次独立调用。理由：既然每次调用的成本几乎都是固定的首字延迟，拆成两次就会把等待翻倍，换来的只是「短输出的那次快一点」。

#### 提示词长度是一个可控项，但不是主因

配对实验（同一张图、同一模型、前后脚）：

| 提示词 | 首字延迟 | 总耗时 | 输出 |
|---|---|---|---|
| 130 字（只问裁切矩形） | 5.9s | 6.4s | 84 字符 |
| 1160 字（原来的完整提示词） | 21.1s | 28.2s | 996 字符 |

提示词长度**确实**影响首字延迟，于是把提示词按「一句一条」重写、压到约 700 字。但重写后同一天又跑出 **43.3s 首字延迟**。所以准确的说法是：**服务端方差是主因，提示词长度是次要项**——重写值得做（它不损伤判断质量），但不能指望靠它解决长尾。

#### 并发：之前的结论过于武断

早先一次探测显示「3 张并发时其中一张 84.2s，而串行是 11.2s」，据此写了「并发更差，不采用」。但后来串行也测到 57.8s——**单次探测不足以支撑那个结论**。目前的处理是串行（不是为了躲限流，而是为了可预期），并且把「排队中 · 前面还有 N 条」显示出来，让人分得清「在排队」和「卡住了」。

#### 裁切判断的精度噪声

同一张高线公园（1600×929），AI 在不同时间给出的照片区宽度是 **68% / 70% / 59%**，人工标注是 69.1%。也就是说这个判断有 **±10 个百分点**的抖动，不是稳定值。处理方式：矩形明显不可信时（宽或高不足 25%）直接不裁用整图；能裁就裁，裁得不合适由详情页换回原图（F5-8，任务 6）。**这是已知限制，不是待修 bug。**

#### 实装后的实测（`app/index.html`）

| 环节 | 实测 |
|---|---|
| 粘贴 → 本地出图（含封面 + 400px 缩略图） | **21ms** |
| 入 items 表（卡片这一刻就可见） | **320ms** |
| 1600px 原件写 item_images | 约 700ms（放在卡片出现之后，不阻塞） |
| 识别成功样例 | 13.1s / 14.1s；失败样例 43.3s、46.5s 超时 |

即 PRD F1-4「本地 ≤1 秒出图入库」成立（≈340ms），且这个数字与 AI 无关。

#### 最终确定的录入流程形态（已落进任务 4）

1. **本地处理不等 AI**：先出图、先落库、卡片立刻可见；AI 字段留 `pending`。
2. **串行调用**，界面显示「排队中 · 前面还有 N 条」与「识别中 · 已 N 秒」。
3. **60s 硬超时 + 降级**：覆盖住观测到的上限（57.8s）。SDK 的 `createStreaming` 会把 `signal` 透传给 `fetch`（已在源码中确认），所以是 `AbortController` **真中断**，不是假超时。超时后封面退回整图、抽屉落兜底、标签留空，并给出「重跑 AI」。
4. **重跑失败不覆盖好结果**：如果这条之前已经识别成功过，重跑失败时只提示「这次没成功，下面是更早那次的结果」，不把状态改成失败。

**已知未解**：来源平台预判有噪声——同一条高线公园素材（网址 `thehighline.org`）第一次判成「公众号」（错），重跑后判成「网页」（对）。字段可改、后果轻，暂不为它加长提示词。

## 5. 分享的实现（任务 7 已完成，2026-09-20）

| 分享类型 | 令牌位置 | 访客看到 |
|---|---|---|
| 收藏夹整体 | settings.share_token | 只读列表页，可按抽屉与标签浏览、可搜索、可翻页，**无任何编辑入口** |
| 单条素材 | items.share_token | 只有这一条，不含其他素材 |

**粒度是「整个收藏夹一个开关」，不做逐条勾选**（用户 2026-09-20 拍板）。上一版这里写的「只返回标记为可分享的素材」是逐条勾选方案的描述，**随该方案被否而作废**——收藏夹分享就是全量只读。

**关闭机制**：`share_enabled` 置否 **或** 令牌对不上 → 立即失效。两个条件都要满足才算有效，所以关闭时只置 `share_enabled=false`、令牌留着不删，链接也已经死了。

**链接形态**：`/s/令牌`（收藏夹）、`/i/令牌`（单条）。分享页同时兼容 `?t=令牌` 与 `#令牌`，因此**平台若不支持路径转发，只需改生成链接的那一处**。

**⚠ 路径式链接的硬前提：资源基准路径。** 浏览器打开 `/s/令牌` 时，页面的「目录」是 `/s/`，页面里所有相对路径（`style.css`、`config.js`、`cards.js`、`store.js`）都会被解析到 `/s/xxx` 而 404 —— **表现是页面卡在「正在打开…」的空壳，不报错**，极易误判成"后端没数据"。修法是在 `<head>` 最前面、任何资源之前动态写入 `<base>`，把基准指回应用目录（`/s/令牌`→`/`，`/app/s/令牌`→`/app/`）。这样根目录与子路径部署都成立。

**访客能看到的边界（必须守住）**：
- 收藏夹分享页：返回全部素材（该收藏夹就是这个人的私有库，没有"部分公开"这个概念）
- 单条分享页：只返回该令牌对应的那一条，其余一概不返回，**也不返回 `settings`**
- 两者都不返回 `ai_raw`、`my_note`（默认关闭）与任何设置表内容
- **访客拿不到 `?id=` 枚举的口子**：分享页点卡片是页内展开详情，不跳 `item.html`；`item.html` 靠 `?id=` 取任意一条，把它交给访客等于顺手给出「改个数字看全库」的办法

**实现要点**：
- `app/cards.js` 被「灵感库」与「分享页」共用 —— 卡的 HTML、侧栏、标签配色只有一份。分享页是对外的脸，靠复制一份 HTML 迟早会长得和主站不一样。
- `share.html` **刻意不加载 `ownerbar.js`**（访客看不到任何解锁入口），但**要加载 `auth.js`** —— `store.js` 的写操作都走 `auth.requireOwner()` 这道门，不加载反而会让分享页成为更弱的一面。
- 分享页带 `noindex,nofollow`：它是发给具体某个人看的，不该被搜索引擎收录。

## 6. 所有者保护（R-1，已于 2026-09-19 决定接受降级）

**这是本方案里唯一一个安全性降级点，必须讲清楚。**

做法：所有者在首次使用时设置一个口令；**口令哈希只存在该设备浏览器本地**（localStorage），写操作前在前端校验。分享视图隐藏所有编辑入口。

**2026-09-20 修订说明**：原方案写的是「前端保存口令的哈希」，但当时设想把它存在数据库的 `settings` 表里。改成路径 A 之后这条不成立了——路径 A 下数据库对所有匿名调用者开放读写，把一个「哈希」存进去既挡不住任何人，又会让人误以为有服务端保护。**因此 `owner_passcode_hash` 字段已删除，口令退化为纯粹的本地门禁。**

**它的真实强度（必须如实理解）**：

| 能防住 | 防不住 |
|---|---|
| 访客随手点开分享链接后乱改 | 懂技术的人用浏览器开发者工具绕过前端校验、直接调用数据接口 |
| 别人拿到网址后误操作 | 有明确意图的恶意篡改（可以改、也可以整库删） |
| 换一台设备访问自己的库（需要口令） | —— |

**为什么第一版可以接受这个降级**：
1. 库里存的是公开渠道收集的设计案例，不是敏感数据
2. 第一版只有一个用户，实际暴露面很小
3. 云服务对数据接口做了来源校验，第三方网站无法直接调用你的数据接口
4. 已实测确认：调用数据接口必须来自本应用的域名，且未登录者只能以 `anon` 角色行动——威胁面是「知道地址且愿意动手的人」，不是「随便一个访客」

**加固路径（保留，随时可升级）**：启用云服务的 Auth 模块，建立**单一所有者账号**，然后把数据库策略从 `USING (true)` 收紧为 `owner_id = auth.uid()`。数据表结构不必改（`user_id` / `owner_id` 列已预留），页面要加一个登录流程。注意这不违反「不做账号体系」——不做的是**多用户**，单所有者账号不构成多用户体系。代价是每个新设备多一次登录。

> **2026-09-20 用户已拍板**：走路径 A（不启用账号），接受上述降级。理由与取舍见 `构建记录.md` #012、#013。

### 9.1 浏览页的两个查询设计（任务 5）

素材体积实测（见 3.6）决定了列表页不能整表拉图片。浏览页因此拆成两步取数：

| 方法 | 取什么 | 为什么 |
|---|---|---|
| `loadIndex()` | 只 SELECT 文本字段、**不含 `cover_thumb`**，按 `created_at desc` | 首屏快；几百条素材也不会一次拖下几十 MB |
| `cardsByIds(ids)` | `.in('id', ids)` 批量取 `id / cover_thumb / cover_source / status / category` | 只给当前页要显示的那些卡取缩略图 |

`ensureCards(page)` 会在批次返回后递归补拉一次：请求在飞的时候新写入的素材，否则会从列表里漏掉。

**侧栏必须包含 AI 新造的标签。** 侧栏标签基于 `countByTag()`（按素材实际打标统计）渲染，而不是遍历 `tags` 表。`tags` 表里没有、但素材上已经有的名字，归到一个叫 **「未分组（AI 新造）」** 的分组里，同样可点可筛。否则这些标签在筛选栏里不存在，F4-3 会静默漏掉一部分内容。

**筛选组合关系**：搜索（F4-1）、抽屉（F4-2）、标签（F4-3，多选）三者之间一律 **AND**；标签多选也是 AND（取交集，不是并集）。叠加关系见 F4-4。

### 9.2 详情页（任务 6）

形态选**独立页面** `item.html?id=N`，不是弹层。理由：单条分享（F6-2）本来就要一个可复制的独立地址，弹层做完到任务 7 还得重做一遍。

**字段的保存时机分两类**，这个区分是照 F5-2 的字面要求来的：

| 类型 | 字段 | 行为 |
|---|---|---|
| 点了就存 | 抽屉、标签增删、来源平台 | 立即写库并刷新界面 |
| 攒着一次存 | 摘要、画面描述、图中文字、备注、来源链接、原文 | 点「保存」按钮 |

一次点击存一次会造成快速连点时请求乱序落库，所以详情页的写操作在客户端排成一条串行链。

**F5-8 换封面只做三件事**（2026-09-20 与用户确认的范围，不含手动框选）：

- **用整图（不裁）** → `cover_source='raw'`，由 1600px 原件整图重做 400px 缩略图
- **按 AI 矩形重裁** → `cover_source='crop'`，矩形取 `ai_raw.rect`；矩形被 `normalizeRect` 判为不可信时会退回整图，此时界面**明确告知是「退了」而不是装作裁了**
- **换哪张图当封面** → 改 `cover_index` 并重做缩略图。多图时才显示这个入口（单图没有意义）

「重裁」只在 `cover_index === 0` 时出现：AI 的矩形描述的是当初送给模型的那张图的版面，换了图之后套用旧矩形式错的。

**一个在真实浏览器里才暴露的 bug（已修，值得记下来）**：左栏原本是 `position:sticky;top:74px`。竖版封面（裁切后 709×860）在 440px 宽的栏里高约 530px，把换封面的两颗按钮推到 679px 处；而 sticky 会把整栏钉住，于是**不管怎么往下滚，按钮都停在 577px 高的视口之外——完全点不到**。
修法是两头收：封面预览限高 `44vh`；跟随滚动只在 `min-height:900px` 时开，并且加上 `max-height:calc(100vh - 92px); overflow-y:auto`。**可达性由结构保证，不再靠估算窗口高度**——只加「窗口够高才钉」的话，多几张图或描述变长又会失效。页面加载后零 JS 报错。

### 9.3 口令门禁（任务 6 提前落地，属 F7）

F5-4（访客隐藏编辑与删除入口）是 P0，没有「谁是所有者」这个概念就实现不了，所以 F7 的口令机制被提前到任务 6 做掉最小可用版本。任务 7 只需在其上加分享链接、只读视图与 F7-4 的输错频率限制。

- 口令的 **SHA-256 存在前端** `config.js`，比对在浏览器里做，解锁状态记 localStorage。R-1 已接受这个降级：它拦的是**误操作与路人**，不是攻击者。真正不可逆的动作（任务 9 发布）单独拿同意，不依赖它。
- **依赖 secure context**：`crypto.subtle` 只在 https 或 localhost 可用。本地走 `127.0.0.1` 没问题；若用局域网 IP 打开，`unlock()` 会明确报错说明原因，而不是静静地永远解锁不了。
- **权限判断只有一处**：`<body>` 上的 `is-owner` / `is-visitor`，配合 CSS `body:not(.is-owner) .owner-only{display:none}`。页面不各自判断「我是不是所有者」——判断散在各页就一定会有漏的。详情页更进一步：访客态下编辑控件**根本不渲染**，不是渲染完再藏。
- **写操作在 `store.js` 一处设卡**（`guard()`）：将来新增写入口会自动被挡住，不必记得每处加判断。

### 9.4 卡片的信息顺序（任务 6 收尾，按用户扫读习惯定）

用户给的顺序是：**抽屉 + 收藏日期同一行 → 项目名 → 摘要 + 标签 → 操作条**。日期从底部操作条挪到抽屉旁边，空出来的位置放项目名。

`228px` 宽的卡片里，项目名和「看原始截图 / 原文」两颗按钮同一行只够显示 5 个字，等于白放。所以操作条整体挪到卡片最底部（`margin-top:auto` + 上边框），项目名独占一行（`13.5px` 加粗、单行省略号）。**这不是审美调整，是宽度算术的结果**——先算清一行能放多少字，再决定谁跟谁同行。

搜索的 haystack 同步纳入 `ai_title`，placeholder 也改成「搜项目名 / 摘要 / …」，否则「有这个字段但搜不到」比没有更费解。

### 9.5 顶栏在窄屏会挤坏（实测发现，已修）

顶栏是不换行的 flex，子项（logo + 导航 + 右侧说明 + 所有者开关）在 `<420px` 时被 flex-shrink 压到内容宽度以下，**「灵感库」被拆成逐字竖排**，同时整页多出横向滚动条。560px / 768px 正常，所以只在手机宽度暴露。

两处修法：

- `.hnav` 加 `flex:none`、`.hnav a` 加 `white-space:nowrap`——宁可挤出去也不能把中文拆成竖排。
- 共享样式里补两级降级（`style.css`，三页同享）：`≤760px` 丢顶栏副标题（`header > .muted`，按位置选而不是给某个 id 打补丁，因为三页副标题写法不一样），`≤460px` 再丢 logo 文字（`font-size:0`，只留图标）并缩导航与按钮字号。

实测 390 / 430 / 560 / 768 / 1280 五档：顶栏高度均为 58px，导航单行，无横向溢出。

**这里踩的坑值得记**：改完 CSS 用 `set viewport` 复测时发现「没生效」，其实是**页面根本没重新加载**——`set viewport` 只改视口，不触发导航。必须重新 `open` 一次才拿到新 CSS。差点据此判断修改无效而回退。

### 9.6 分享页的实现（任务 7）+ 两个实测踩到的坑

代码结构：新增 `app/cards.js`（公开渲染模块）与 `app/share.html`（访客页）。

`cards.js` 的接口：`esc / fmtTime / toDataUrl / tagChip / counts / navCatsHtml / navTagsHtml / cardHtml / haystack / matches / emptyHtml / countText`。其中 `cardHtml(it, thumbRow, tax, opts)` 的 `opts={readOnly, actions, openAct}` ——**访客态靠 `readOnly:true` 收起主站才有的「看原始截图 / 原文」按钮**，否则访客会以为这里是能用的一整套应用。

`share.html` 的四种入口归一：`/s/令牌` → 收藏夹；`/i/令牌` → 单条；`?t=令牌` 与 `#令牌` → 不知道哪种，先当收藏夹校验、再当单条查（两个命名空间都是随机令牌，撞车概率可忽略）。

**坑一：空壳不报错 —— 路径式链接下资源全 404**

路径式链接打开后页面卡在「正在打开…」。原因是浏览器把页面「目录」认成了 `/s/`，页面里所有相对路径被解析到 `/s/style.css`、`/s/config.js` …… **全部 404，本地脚本一个都没跑起来**（只有 CDN 那个绝对地址的 SDK 加载成功，所以更迷惑——看起来"网络是通的"）。**症状是空壳而不是报错**，不逐项点开就会误判成"数据库没数据"。

修法：`<head>` 最前面、任何资源之前动态写入 `<base>`：

```js
var p = location.pathname, i = p.search(/\/(s|i)\//);
var dir = i >= 0 ? p.slice(0, i + 1) : p.replace(/[^/]*$/, '');
document.head.appendChild(Object.assign(document.createElement('base'), { href: dir }));
```

`/s/令牌` → `/`；`/app/s/令牌` → `/app/`；`/app/share.html?t=令牌` → `/app/`。根目录与子路径部署同时成立。

**本地服务 `_serve.py`**：把 `/s/*`、`/i/*` 重写到 `share.html`（**保留浏览器地址栏**，分享页才能从 pathname 读到令牌）。同时支持 `PORT` 环境变量与 `0.0.0.0` 绑定，作为任务 9 发布入口的雏形。

**坑二：CSS 类名撞车（同一个 `empty` 身兼两职）**

分享页截图暴露出「画面描述」「图中文字」两个空字段各占两百多像素高、内容还居中。根因是**一个类名被用在了两种语义上**：

| 用法 | 元素 | 期望样式 |
|---|---|---|
| 整页空态（"没找到，试试换个词"） | `.empty` | `text-align:center; padding:80px 20px` |
| 空字段小字 | `.ro.empty` / `.csum.empty` / `.sum.empty` | 只要灰一点的小字 |

后三者都带 `empty` 类，于是把前者的 80px 内边距与居中一起继承了。**这个 bug 在任务 6 的详情页就已存在**，只是当时没逐字段量高度；分享页把它放大成"访客看到一整屏空白面板"，才被看见。`csum.empty` 那条更隐蔽 —— 它会让「没有摘要」的卡片整体被撑高，而当前 3 条素材都有摘要，属于潜伏状态。

修法：整页空态改名 `.emptystate`（`style.css` 1 条规则 + `index.html`、`share.html` 共 3 处 `class`），其余保持原样。实测 `.ro.empty` 高度 228px → 21px。

**教训**：给"状态"起类名时不要用 `empty` 这种通用词。同一套样式表里，通用词一定会被别处复用，而复用的时候没人会去查它原本绑了什么样式。

### 9.7 口令输错频率限制（F7-4，任务 7）

用户定的档位：**连错 5 次锁 60 秒**。

- 计数 `elangit.owner.fails`、锁定时刻 `elangit.owner.lockUntil` 都写 localStorage —— **刷新页面不能绕过**。若只放内存变量，按一下 F5 限制就没了，等于没做。
- 锁定期内 `unlock()` 连哈希都不算，直接返回 `false`：让「锁定」在代码里是显式一步，而不是靠界面自觉不去调用。
- 触到上限时把计数清零、开始计时：锁是这一轮的结束，解锁后重新从 0 数。
- 界面显示实时倒计时（`setInterval` 每秒走）。定时器必须是**模块级变量**：`paint()` 会换掉顶栏整块 HTML，局部变量管不住它，会漏出一个永远在跑的定时器。
- **不做递增惩罚**：用户只指定了这一档，多出来的档位属于没被要求的行为。

**如实记录它的强度上限**：这是**纯前端限制**。清浏览器数据、或直接在控制台调 `auth.unlock()`，都能重置。拦的是手滑，不是破解。

### 9.8 埋点、改动对照与数据页（任务 8）

#### 1）F2-8「改动差异」为什么是派生，不是事件

任务表里原来写的是「F2-8 改动差异落库」，实装时推翻了这个说法。**差异是当前状态的函数**：`items.ai_raw` 是 AI 当时说了什么，`items` 上是现在是什么，一比就是差异。存成事件流反而多一份会漂移的副本——改两次就得靠事件顺序才能拼出「现在的差异」，而直接对比永远不会不一致。

于是比较规则单独成一个模块 `diff.js`，**详情页与数据页共用**。不共用的代价是具体的：详情页说「改了 3 处」、数据页说「改了 2 处」，同一份数据两个答案，比没有这个功能更糟。

比对哪六个字段：项目名称 / 摘要 / 画面描述 / 图中文字 / 抽屉 / 来源平台（比对对象是 `ai_tags`，不含 `my_tags`——用户自己加的标签不是对 AI 的否定，没有「AI 原值」可对照）。`my_note` / `raw_text` 同理不在内。

**没有 `ai_raw` 的素材要如实说「没留下来」，不能写成「没改过」**——后者是在断言一个不知道的事实。`ai_raw` 是 v7 才加的列，库内 3 条存量素材全是 NULL，数据页据此显示「还没有样本」而不是「0% 修改率」。

#### 2）A14 的真修（原代码在换过封面后永远修不好）

**症状**：截图类素材换了封面图（`cover_index = 1`）之后，详情页的「按 AI 矩形重裁」点不动。

**根因**：矩形的唯一来源是 `items.ai_raw.rect`，那是「**送进模型那张图**」的矩形；而重裁的守卫条件写的是 `rect && cover_index === 0`。用户在详情页把封面换成第 2 张图，`cover_index` 变成 1，条件永远不成立。换句话说，**换过封面就再也修不回来了**，而「换封面」正是最容易需要重裁的场景。

**修法（两层）**：

1. `item_images` 加 `ai_rect` 列，矩形**按图存**（见 3.2）。重裁的对象从「第 1 张」改成「**当前封面那张**」（`state.item.cover_index`），守卫条件里的 `cover_index === 0` 删掉。
2. 目标图还没有矩形时，用 `ai.js` 新增的 `detectRect()` 现场问一次（短提示词，只要矩形，比完整识别快得多），问完写回 `item_images.ai_rect` 并缓存。界面上这就是「让 AI 判这张图的画面区（要等一会儿）」这个按钮。

**实测**：对 #2（纽约高线公园，封面是第 2 张图）点一次 → 约 10 秒 → 封面按 AI 矩形重裁，比例 400×369；库里 `item_images seq=1 ai_rect={"top":0,"right":63,"bottom":100,"left":0}`、`cover_source='crop'`；`cover_replaced` 事件带上 `reason='recrop'` 与 `rect_fresh=true`。**这条验收项现在是可修的了，任务 6 时它是修不了的。**

#### 3）E10（访客访问分享）为什么不做

和 F6-6 同一个理由：事件表是 `anon` 可写的（不做账号体系就没有别的选择），**匿名写入意味着客户端可以伪造任意一条**。在一个能自己造数的表上统计「分享被看过几次」，得到的数字不可信，而不可信的数字比没有数字更坏——它会以「数据」的样子被引用。

代价要说明白：**这一版拿不到分享的实际价值量化**。真要，得先有账号体系（v2），或者在分享页上让访客写一条带服务端校验的记录。

#### 4）埋点失败必须旁路

`track.js` 的硬约定：**任何埋点写入失败只 `console.warn`，不 reject、不 throw**。调用方是录入、搜索这些主流程，记录行为不能反过来把它们搞坏——埋点是观察者，不是参与者。`store.insertEvent()` 因此对访客返回 `false` 而不是抛错。

#### 5）实测踩到的两个坑（都会静默丢数据）

**坑一：E7 在跳转前发请求，必然被取消。** `search_result_click` 的语义是「从搜索到点开的耗时」，所以它得在点卡片、`location.href` 跳转**之前**发。但浏览器在页面卸载时会取消未完成的 `fetch`，于是这条事件**系统性地一条都到不了库**——而它恰恰是 A4 唯一的判据。修法：`goAfterLog(href, logPromise)`，先把写入发出去并给 400ms 预算，然后才跳转。实测 `ms=2264` 正常落库。
（这不是埋点的坑，是「用跳转前的最后一个请求做记录」这件事本身的坑。）

**坑二：`session()` 的顺序写反了。** 原实现先写 localStorage 的「今天已记过」标记、再调 `event()`，而 `event()` 对访客返回 `false`。结果：**访客访问一次，标记照样落上**；所有者随后在同一天打开，`session_open` 就被这个标记挡掉了——日志里一条都没有，看起来像功能没做。修法：先 `isOwner()` 判断，**写入成功之后**才落标记。

#### 6）数据页的取数口径

| 面板 | 数据来源 | 样本不足时 |
|---|---|---|
| 验收进度（A1/A2/A4/A12/A13） | 事件 + 素材 | 直书「样本不足（n / 目标）」 |
| 每日录入条数（A12） | `items.created_at` | 看的是**有没有掉零**，不是总量 |
| AI 字段修改率（A2） | `diff.summary()` | 「还没有样本」，不含 NULL 的素材进分母 |
| 找回效率（A4） | E6/E7 配对 | 「还没有搜索记录」 |
| 兜底抽屉占比（A11/A13） | `items.category` | 库内条数不足 30 时注明 |
| 封面人工兜底（E13） | E13 | 「还没有人工换过封面」——这是好事 |

取数只走 `reportItems()`（**不带图片**，`ai_raw` 必须带）。日期分组用**本地时间**，不用 UTC——否则晚上 8 点后录的素材会被算到第二天，「连续两周」直接判错。
