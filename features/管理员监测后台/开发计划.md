# Elangit 管理员监测后台｜开发计划

> 状态：Q1–Q3 已由 Elan 于 2026-09-24 按推荐方案确认。首期报表与新埋点隐去搜索原词已在本地实现；WorkBuddy 复核后的修正已完成本地回归。**未执行 SQL、未改线上数据、未发布。公开仓库同步状态以 GitHub Desktop 中的仓库历史为准，不在计划里固定可变 commit hash。**

## 1. 目标、现状与反对意见

目标是让 Elan 看清「素材是否找得回、项目筛选是否有用、哪些环节需要改」，并能按条件调取明细。首期只做**本人使用数据的报表**：总览、找回与内容使用、项目使用、事件明细、原有产品验收、筛选和 CSV 导出。推广来源、访客转化、注册留存留作后续指标；目前不采集时显示「未采集」，不能画成 0。访客分享访问 E10 仍不计数，因为匿名写入可伪造，现有 PRD 已明确不做（`docs/06-技术方案.md` §9.8「E10」）。

**反对把 Auth 作为报表一期的前置条件。** 现有 `app/stats.html` 已用 `items` 和 `events` 出报表，扩展筛选、口径和导出不需要先改权限。原计划让 Auth 能力验证失败阻止报表上线，颠倒了产品价值和安全改造的依赖。Auth 应另立权限加固项目，由 Elan 改写既定边界后再做。

**首期不能宣称「只有管理员能监测」。** 当前 `app/stats.html` 的 `isOwner()` 是前端显示门禁；`data/schema.sql` 的 9 张表均把读写权给 `anon`，策略为 `USING (true)`。公开发布的 `publishableKey` 不是秘密，懂技术的调用者可绕过页面读取或篡改数据。此风险已在 `AGENTS.md` §4 事实 5、§10 和 `docs/06-技术方案.md` §6 接受并记录。首期界面可以只向已解锁者显示，但必须写明它不构成数据库权限边界。`items` 含私人备注、`item_images` 含 base64 原图，因此**不向新增埋点写入更多敏感正文或令牌**。

当前埋点在用户执行录入、检索等动作时写入，不要求先打开 `stats.html`；但 `track.js` 仍检查已有的前端所有者解锁状态。解锁标记保存在 `localStorage`，刷新后保留，直到主动锁定或浏览器数据被清除。因此普通已解锁设备可持续记录；新设备、清缓存或尚未解锁时的操作不会记入。没有服务端身份时，不能一边可靠识别「这是 Elan 本人」、一边把采集完全与所有者状态解耦；此限制不应被包装成已解决。

### 单一口径的可执行验收

- **A1**：只认最早的、`props.ms_from === 'input'` 且耗时有效的 `item_create_finish`；不能混入旧的页面打开起点。
- **A2**：`ai_raw` 缺失表示「没留下原值」；字段可用率分母只算 AI 实际产出非空内容的样本，`diff.js` 所需现值列必须全取齐。
- **A4**：只用 `search_attempt_end`（E14）结算，`timeout` 与 `abandoned` 算失败；不能用 E6／E7 拼一个较好看的比率。
- **A13**：未到门槛为「样本不足」，达到门槛为「待人工复盘」，没有人工记录时不得自动写「已通过」。
- 用现有 `_verify_stats.html`／`_verify_stats_ui.html` 的同一组临界样本对比新旧页面输出；上述判据必须逐项断言，不能只比页面是否渲染成功。

## 3. 事件与调取方案

**沿用 `events`，不新建表、不迁移历史事件、不加数据库列。** 它已有 `id`、`name`、`at`，`props` 已有 `sid`、`device`，检索事件还有 `search_id`。实际实现把 `page`（固定页面类别）、`event_version`（当前为 `1`）、`channel`（当前为 `null`）放进 `props`；旧事件缺失的维度显示「未记录」。不保存可能含 `/s/`、`/i/` 令牌的完整 URL。渠道尚未采集，不能据空值推断「直接访问」。项目数、项目素材数、AI 修改率等能从现表状态派生的值不另落事件（`AGENTS.md` §4 事实 6／7）。

`events.user_id` 目前固定为 `local-owner`，首期不另加 `owner_id`。若以后引入 Auth，`owner_id TEXT NOT NULL DEFAULT auth.uid()` 应**接替**这列的身份含义：迁移存量行归属、修改写入与查询后，移除或明确废弃旧 `user_id`，不得让两列同时充当鉴权依据。平台数据库规范见 `references/database/code-generation.md` §Auth Gate／Modeling Conventions 和 `references/database/management.md` §RLS。

**CSV 调取**：页面提供「当前筛选明细」和「按日汇总」两种下载，沿用画面上的日期、事件、页面、设备、渠道条件；导出字段白名单排除图片、原文、备注、分享令牌、搜索原词、未审查的 `props` 全量和 AI 原始错误文本。文件以 UTF-8 BOM 开头；含逗号、双引号、回车或换行的文本加双引号，内部双引号写两次；对会被 Excel 当公式的文本做安全转义。明细同时导出「日期（Asia/Shanghai）」及「发生时间（UTC，ISO 8601）」两列，便于与上海日期汇总对齐且保留原始时间；未知值留空字段而非伪造「0」。事件明细页面也不展示历史事件中的原始 `props.q`。

现有 `store.loadEvents()` 只取最近 60 天、最多 2000 条（`app/store.js`），不能拿它直接导出全量。当前报表先查询精确总数，并把事件最大 `id` 作为上界；随后以 `id` 升序按 offset 用 `.range(offset, end)` 分页。每页核对精确总数与预期页长、全程检查唯一 ID，最后再次核对总数；在读取期间行数变化、页长异常或出现重复时明确报错并要求刷新，不静默导出截断数据。新插入且 ID 高于起始上界的事件不进入本轮读取。

当前客户端批次为 200 行，页面展示为每页 50 条；**平台最大 `.range()` 页长没有权威依据，标为存疑**。WorkBuddy 复核确认当前验证台自定义了 count 与 range 语义，因此 8/8 只证明实现与 mock 相符，不能证明云端行为。后续若要消除该未知，先由 Elan 明确授权一次最小只读核对：`select('id', { count: 'exact' })` 读取一行并检查真实 count 返回字段，再执行 `.range(0, 1)` 检查边界语义；不执行 SQL、不写数据。最大页长仍需另行实测。多次请求不是同一个数据库事务快照；并发更新字段、或读数变化后又恰好恢复同一总数时，无法保证严格快照一致性。报表目前把完整事件集加载到浏览器后再按日期与维度筛选和导出，随历史数据增长会增加内存与读取时间；真实库规模表现尚未测。若达到实际性能边界，再改成服务端筛选／可续传导出，并先实测平台能力。审计级一致性需另设计服务端快照导出。

**已定：新埋点不记搜索原词。** 现有 `app/library.html` 把 `q` 写入 E6、E8，`app/track.js` 又把它写入 E14；实施时三处须一起改，只记词长、是否有筛选、结果数和结算结果，不记可反推常见短词的哈希。保留现有 `search_id`、`outcome`、`ms` 等找回口径，不因删除原词破坏 A4。历史 `props.q` 已在库中，首期只在报表明细和 CSV 中屏蔽，不擅自修改或删除旧数据；是否清理历史值与保留期限需另行确认。此前计划的「保留 30 天并自动清理」无依据，WorkBuddy 的 Database／Auth／Storage／LLM 模块也没有定时任务能力，不能写成首期承诺。

**历史结果数不可直接连成趋势**：旧 E6／E8／E14 使用 `props.n`／`props.total`，2026-09-24 起的新事件使用 `result_count`／`total_count`。A4 只读 `outcome`／`ms`，其判据不受影响；若后续新增结果数时间序列，必须把字段口径切换日期标出来，不得把两种字段直接合并比较。

## 4. 本方案触及的边界变更：权限加固单独立项

**Q1 已定：首期不引入账号，权限加固以后单独立项。** `AGENTS.md` §8 第 2 条明定第一版「不要加账号体系／多用户」，`docs/06-技术方案.md` §6 保留了「单一所有者账号」的加固路径，但未来真正启动时仍须由 Elan 单独批准这项边界变更。平台**没有管理员角色**；只能建立单一所有者账号，数据库以 `owner_id = auth.uid()` 判断归属，`owner_name` 只是显示名，不参与鉴权（平台 `references/database/management.md` §RLS）。

`owner_id = auth.uid()` 只能保证「用户访问自己名下的行」，**不能单独保证只有 Elan 一人能创建数据**：可注册的其他账号也能在普通 owner-only 策略下创建自己的行。若坚持单一所有者，还须设计只允许 Elan 的固定 UID 写入受保护表；这个身份名单和注册入口并存的产品含义要由 Elan 决定，不能把数据归属误当管理员角色。

代价必须先接受：平台 Auth 只支持**已注册的 HTTPS 发布域名**，localhost／预览无法验证；登录与注册入口又必须可见或可直接到达（平台 `references/auth/code-generation.md` §Availability Boundary／Default Login UI Contract）。这与「只有 Elan 一人使用、不对外开放注册」有正面冲突，不能在计划里假设注册入口可暗藏。登录链路只能在 Elan**另行批准发布后**做线上验证，顺序无法改成「本地全部验完再发布」；其他逻辑仍应先在本地验完，线上 Auth 验证失败时按预定回退方案处理。此限制与入口代价均须 Elan 接受后才立项。

**Q2 方向已定：若将来加固，一次覆盖全部 9 张表。** 登录、共享客户端 session、各页读写门禁改造是主要成本，只锁事件却留下含备注、原图的素材库可由匿名读写，收益与代价不相称。届时一次审查并改造全部 9 张表的 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 的 GRANT 与 RLS；要挡匿名访问，受保护表只授予 `authenticated`，不能保留 `anon` 的旧授权和 `USING (true)` 的全开策略。不同表可以有明确的公共只读例外，但不能遗漏匿名写入、更新或删除。平台规则见 `references/database/management.md` §Roles／Common shapes；现状见 `data/schema.sql` 权限段。

同一轮应把**新增 Auth 作为素材编辑与监测读取的唯一权威身份**，逐页替换现有前端口令状态和 `store.js` 的 `guard()`；前端口令最多作为额外的误操作锁，不能与 Auth 并列成为第二套权限事实。埋点应随应用内已登录所有者的正常使用而记录，不能依赖是否打开后台。新设备或清空浏览器后、尚未完成登录时，使用行为会漏记；使用平台持久 session／刷新能力并明确提示重新登录可缓解，但不能把漏记算作「没有使用」。

### 先解决令牌分享，再收紧全库

RLS 只看行和登录身份，**拿不到 URL 里的分享令牌**。若把 `items` 等表改成 owner-only，现有 `/s/令牌`、`/i/令牌` 会断，待做的 `/p/令牌` 也无从读取。`app/_serve.py` 目前仅重写 `/s/`、`/i/` 路径并提供 `/api/meta`、`/api/img` 抓网页端点，没有数据库读取能力。Elan 已同意**优先评估令牌校验方案**；下表保留备选及代价。未来权限项目须先验证所选方案并取得单独实施授权，再执行全库收紧。

| 方案 | `/s/`、`/i/`、`/p/` 的处理 | 代价／风险 |
|---|---|---|
| 公共读＋所有者写 | `/s/` 可继续读整库；`/i/`、`/p/` 若靠 `share_enabled` 布尔列开放行，所有被分享过的素材／项目可被匿名列举 | 改动较少，却不能保证单条／项目令牌的私密性；关闭分享时还需严格撤回公共可读状态，**不推荐作为私有分享方案** |
| 令牌校验 RPC（建议优先评估） | 匿名用户只可调用按令牌查 `/s/`、`/i/`、`/p/` 的窄接口；底层表不给匿名直接读，函数只返回分享允许的字段与图片 | 平台支持 `cloud.database.rpc()` 与 `SECURITY DEFINER`，但后者会绕过 RLS；必须限制函数 `EXECUTE`、校验令牌、限制返回字段、分页并测试撤销与猜测令牌。启用 `SECURITY DEFINER` 属高风险 SQL，实施时须展示精确语句与影响并取得明确确认。平台依据：`references/database/management.md` §Custom PostgreSQL Functions／Dangerous SQL |
| 扩展现有 Python 服务读库 | `/s/`、`/i/`、`/p/` 由服务端校验令牌并查库，浏览器只拿经筛选的结果 | 可控制响应与限流，但现有 `_serve.py` 无数据库凭据／连接；平台是否提供合适的服务端访问路径为【待验证】，且增加服务端维护面 |

若选择 RPC 或服务端读取，`/s/` 可和 `/i/`、`/p/` 一样走令牌校验；若选择公共读救 `/s/`，须明确「整库内容可被匿名直接列举」，不能把分享令牌误称为整库访问控制。权限迁移按单语句执行、逐项回读 GRANT／RLS／策略与真实匿名／登录请求；不能用页面隐藏来代替数据库拒绝。
