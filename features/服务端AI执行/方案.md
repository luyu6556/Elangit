# 服务端 AI 执行 · 方案（v0.1 · 待 Elan 确认）

> 2026-09-24 夜 拟定。**本文件只做设计与拆解，不动代码。**
> 起因是 Elan 的一句原话：「我不可能一直打开这个页面等它。」
> 相关台账：`docs/10-问题台账.md` 的 B-001 / B-003 —— 那两个修的是**一致性**（谁在跑、会不会重复跑），
> 本方案要动的是更根本的一层：**执行者本身**。

---

## 0. 为什么做

### 0.1 现状：AI 的执行者是浏览器页面

2026-09-24 一晚修了三轮（B-001 库侧队列、B-003 过期租约接管），队列的一致性已经通了：不会重复跑、执行者死了能被接管。但**执行者始终是一个打开的网页**。页面不在了，任务就停在那儿。

### 0.2 实测证据（Elan 同一晚做的对照实验）

两次上传，唯一变量是「页面有没有被动过」：

| 素材 | 操作 | 结果 |
|---|---|---|
| id=51 | 页面不动 | **26 秒**完成 |
| id=52 | 中途刷新 + 切换页面 | **3 分 38 秒**完成 |

id=52 的 3 分 38 秒拆开看（`events` 表逐条）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 第一次调用被刷新打断 | ~110s | 22:55:34 开始，22:57:24 页面重载，那次白跑 |
| 等租约过期 | ~40s | 租约 150 秒，新页面判定「有人在跑」，只能干等 |
| 等用户打开下一个页面 | ~30s | 必须**再打开一个页面**才会有人接手 |
| 真正跑 AI | 38s | 22:58:34 在素材库页接管，22:59:12 完成 |

**3 分 38 秒里只有 38 秒真的在跑。** 这不是 bug，是「执行者是页面」这个前提的必然结果：任何页面的消失或切换都会让任务停在半路，而恢复必须等到「有人再打开一个页面」+「租约过期」。

### 0.3 目标（一句话）

**提交之后可以关掉浏览器走人，AI 照样跑完。**

## 1. 验收判据

方案做完要能被证伪，所以先写判据：

1. **主判据**：提交一条只填网址的素材 → **立即关闭所有 Elangit 页面** → 60 秒内（不含 AI 本身耗时）该条 `items.status` 变成 `done`，且 `ai_digest` / `ai_title` 都有值。**全程不依赖任何页面打开。**
2. **不回归**：前端队列照常工作；同一条素材**不会被跑两次**（`ai_attempts` 增量与实际写入次数一致；`events` 里 `ai_process_done` 只出现一次）。
3. **一致性**：同一批模型输出样本，服务端与前端解析结果**逐字段完全一致**（见 3.2 的一致性验证台）。
4. **可恢复**：服务进程重启后，仍处于 `pending` 的素材会被继续处理。

## 2. 已探明的事实（2026-09-24 23:0x 探针实测，可复现）

服务端能不能自己干活，是这套方案成立的前提。已经用 Python 标准库（无第三方依赖）实测过：

### 2.1 服务端读库 —— 通过

```
GET {endpoint}/.cloud/database/rest/items?select=id,status&order=id.desc&limit=2
Header: x-wb-webapp-access-key: <publishableKey>
→ HTTP 200，返回 JSON 数组
```

**关键点**：认证头名是 **`x-wb-webapp-access-key`**。此前用 `apikey` 或 `Authorization: Bearer` 手搓 REST 会拿到 **401 invalid_client**（2026-09-24 20:5x 实测），那是头名不对，不是端点不可用。头名来自 SDK 源码里的 `var pe="x-wb-webapp-access-key"`。

### 2.2 服务端调 LLM —— 通过

```
POST {endpoint}/.cloud/llm/chat/completions
Header: x-wb-webapp-access-key: <publishableKey>
        Content-Type: application/json
        Accept: text/event-stream
Body:  { model, messages, stream: true, response_format: {type:"json_object"} }
→ HTTP 200，content-type: text/event-stream
```

**实测读数**（2026-09-24 23:0x，最小请求）：HTTP 200、SSE **479 行**、总耗时 **3.7s**、首字 **3.4s**、输出 JSON 正确。

**两个硬约束**：
1. **必须 `stream: true`**。传 `stream: false` 会返回 **400 `request_stream_required`**（实测）—— SDK 内部也是强制覆盖成 `true` 的（`n.stream=!0`）。
2. 端点前缀：SDK 里 `database: ${endpoint}/.cloud/database/rest`、`llm: ${endpoint}/.cloud/llm`。

### 2.3 服务端写库 —— **未实测，是第一步要验的**

`PATCH /.cloud/database/rest/items?id=eq.<id>` 加同样的头，预期可用（与 GET 同源同认证），但**没有实测过**。开工第一件事就是验它，不通过则本方案整体不成立。

### 2.4 已有的队列机制（本方案要复用，不要重造）

`items` 两列（2026-09-24 加，见台账 B-001）：

| 列 | 语义 |
|---|---|
| `ai_lease_until` | 认领租约的到期时刻。**认领条件：`status='pending' AND ai_lease_until IS NULL`**（乐观锁） |
| `ai_attempts` | 认领次数，≥3 落 `failed` |

**接管条件**：`ai_lease_until < now`（执行者死了，租约没人放）。
判空**必须**用 `IS NULL`，写成 `= NULL` 会报 22007（Postgres 语义）。

## 3. 设计

### 3.1 总体：让服务端成为「另一个执行者」

不去动前端的队列，而是在 `_serve.py` 里起一个后台 worker，**用同一套租约条件去抢同一批 pending**。

好处是：

- 前端逻辑一行不用改（`aiqueue.js` 的 `sweep` / `claim` / `steal` 照旧）；
- 去重**天然成立**：两边抢的是同一个 `ai_lease_until IS NULL`，抢到行的那个才跑；
- 执行者死了照样能被接管（租约到期），不引入第二套协调机制。

```
        ┌──────────────┐        ┌──────────────────┐
        │  浏览器页面    │        │  _serve.py worker │
        │  aiqueue.js  │        │  (新)            │
        └──────┬───────┘        └────────┬─────────┘
               │  claim/steal            │  claim/steal
               └───────────┬─────────────┘
                           ▼
                  items (pending + ai_lease_until)
                           │
                    谁抢到谁跑，另一个拿到 0 行即退出
```

### 3.2 提示词与解析的单一真源 —— **本方案最大的设计问题**

服务端跑 AI，就得在 Python 里**再写一遍**：提示词拼装、JSON 容错提取、抽屉白名单校验、digest 三段严格校验、标签去重与截断、标题清洗。

这正是这个项目已经吃过两次亏的地方：

- 2026-09-24 B-003：`stealAi()` 写了却没接进 `sweep()` —— 两处逻辑，一处漏了；
- 2026-09-24 `add.html` 的 `runAi` 与 `aiqueue.js` 的 `execute` 一度并存，第一版就漂出了「复用精简行导致模型收到空输入」的 bug。

所以**不允许**「Python 抄一遍、以后各改各的」。三个选项：

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | Python 移植解析函数 + **跨语言一致性验证台**：同一批模型输出样本分别喂给 JS 与 Python，断言逐字段一致 | 可验证、可执行；多花一个验证台的工，但把漂开变成**能被红掉**的问题 |
| B | 服务端调 Node 跑解析 | 平台当前只配了 `python3 _serve.py`，引入第二运行时与依赖，收益不抵成本 |
| C | 服务端只存原始 JSON，由前端「消化」 | 违背目标——前端不开就永远消化不了 |

**提示词同源**：把提示词抽成一份 `ai_prompt.txt`（真源），JS 侧 `fetch('/api/prompt')` 取、Python 侧直接读文件。**任一时刻只有一份**。

### 3.3 分期：第一期只做「无图素材」

| 素材类型 | 谁跑 | 为什么 |
|---|---|---|
| **只填网址（无本地图）** | **服务端**（第一期） | 正是 Elan 的痛点场景；输入是纯文本，Python 端不需要任何图像处理 |
| 截图 / 有本地图 | 前端（维持现状） | 需要 canvas 做 1000px 输入压缩与封面裁切矩形；Python 端做这个要引入 Pillow 等依赖（平台 `installCmd` 当前为空） |

一期判据里「关掉页面也能跑完」只承诺无图素材——**这一点必须在文档和界面文案上说清楚，不能含糊**。

### 3.4 触发与调度

- worker 每 **10 秒**扫一次 `status='pending' AND ai_lease_until IS NULL`（取最近若干条，串行跑）。
- 进程启动时先扫一次（覆盖「重启前留下的 pending」）。
- **平台可能休眠进程**：休眠期间不会跑，这是平台限制不是缺陷。兜底是「任何页面请求都会唤醒进程」，worst case 退化成今天的行为。**必须写进交付说明，不许说成"永远在跑"。**
- 可选加速：`add.html` 入库后 `POST /api/ai/kick` 触发一次立即扫描（省 10 秒轮询）。**列为可选，不进一期必做**。

### 3.5 超时、失败与判死

- 单次调用超时 **90 秒**（与 `config.aiTimeoutMs` 对齐，改一处要同时改 `config.js` 与 `_serve.py` —— 这条也要进一致性验证台）。
- 失败：`status='failed'`、`ai_lease_until=null`、`ai_attempts+1`；≥3 次不再自动重试。
- **已有结果的不许被失败覆盖**（重跑失败不能把 done 打成 failed），与前端同一判据。

## 4. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| 1 | 两套解析逻辑漂开（**最高风险**） | 3.2 选项 A 的一致性验证台；提示词抽成单文件 |
| 2 | 服务端与前端同时跑同一条 | 复用同一套乐观锁条件，禁止写「只看 status='pending'」的简化认领 |
| 3 | 平台休眠 → 任务看似"没跑" | 交付说明写明；不要把「关页面也能跑」说成「永远在跑」 |
| 4 | `_serve.py` 从"静态服务+两个小接口"变成"带后台线程的服务" | worker 全部异常必须吞掉并记日志，绝不能让线程异常影响 HTTP 服务；线程内不持有共享可变状态 |
| 5 | publishableKey 出现在服务端 | 它本来就在 `config.js` 里随前端公开下发（RLS 为 `USING(true)`），服务端读同一份配置即可，**不要新建第二处存放** |
| 6 | 写库失败导致素材卡死 | 与前端一致：失败也要释放租约并落 failed |

## 5. 任务拆解（交给接手的 Codex）

> 顺序即依赖顺序，前一步不成立就不要往下做。

1. **前提验证**：服务端 `PATCH` 写库是否可用（`x-wb-webapp-access-key`）。用一个无害字段实测，验完还原。**不通过就停下来重新定方案。**
2. **提示词单源化**：抽 `ai_prompt.txt`，`ai.js` 改为 fetch 它，Python 读同一文件；两边的提示词拼装结果要能被断言比对（含 `hasImage` 两种分支）。
3. **Python 侧实现解析**：移植 `extractJson` / `normalizeCategory` / `parseDigest` / `normalizeTags` / `normalizeTitle` / `normalizePlatform`，逐条对着 `ai.js` 的注释（那里写着每条规则的来龙去脉，不要凭直觉简化）。
4. **跨语言一致性验证台**：一份样本集（含合规/不合规/乱序/数组/空值/超长/越界抽屉等边界，直接取 `_verify_ai.html` 的用例扩写），JS 与 Python 各跑一遍，断言逐字段一致。**这是本方案的质量闸门。**
5. **`_serve.py` 加 worker**：轮询 → 乐观锁认领 → 跑 AI（SSE）→ 写回 → 释放租约；启动先扫一次。
6. **本地端到端验证**：`cd app && python3 _serve.py`，录一条只填网址的素材，**立刻关掉所有页面**，观察库里是否在 60 秒内变 `done`。
7. **线上发布 + 线上验证**：发布后真机复现第 6 步（这是 Elan 唯一认的验证方式）。
8. **回写台账**：新增 `B-005`（或对应编号），六段式；构建记录追加一条。

## 6. 明确不做（第一期）

- 有图素材的服务端处理（图像压缩 / 封面裁切矩形）—— 需要第三方库，且不是本期痛点。

- 改动前端的 `aiqueue.js` 机制（它是本方案的协调基础，动它等于同时改两边）。
- 把「页面打开时才有人跑」这个兜底路径删掉（两条路都要留着，互为备份）。
