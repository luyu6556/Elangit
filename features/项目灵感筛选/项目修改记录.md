## #001｜2026-09-22｜需求草案建立

**背景**

用户提出：灵感库的价值不止在于积累与找回，也应帮助设计项目启动。用户希望每次进入灵感库时可以新建项目，以书籍翻页式的单卡浏览既有素材，进入详情判断后，将适用的素材收藏进当前项目。

**本次变更**

1. 建立独立目录 `features/项目灵感筛选/`。
2. 新增 `PRD.md`（需求草案 v0.1）与本记录文件。
3. 草案提出“`projects` + `project_items` 多对多关联”的数据方向：项目收藏只建立关联，不复制、移动或改写既有素材。
4. 明确左右翻页只负责浏览，不暗含喜欢／不喜欢／排除；收藏必须由用户显式点击。
5. 明确从翻阅页进入素材详情再返回时，应恢复至同一项目、同一张卡。

**原因与取舍**

若把项目 ID 或项目收藏状态直接写入既有 `items`，同一素材被多个项目引用时会互相覆盖，也会污染原灵感库的浏览、分享与数据口径。独立关联表能保持原素材为唯一真值，同时满足一个项目收多条素材和一条素材进入多个项目的需要。

**影响范围**

本次仅新增方案文档，未改动 `app/`、`data/schema.sql`、现有 `docs/`、数据库或线上应用。

**验证／待验证**

- 已确认：独立 PRD 与修改记录文件已建立。
- 待确认：项目名称／构思的必填规则、一个素材是否可用于多个项目、翻阅范围、已收藏素材的翻阅策略、跨设备续读、项目归档／删除，以及项目素材集是否需要排序／导出／分享。

**下一步**

根据用户对待确认事项的答复，将 PRD 升级为可评审版本；获得明确开发同意后，再提交数据迁移、页面原型、实现步骤和验证计划。

## #014｜2026-09-23｜一期迁移线上执行与回读验证

**背景**

一期页面（项目建立、标签筛选、快速翻阅、项目素材集）必须建立在 `projects` 与 `project_items` 两张新表上。在写任何依赖新表的数据访问代码之前，必须先把迁移真正落到线上库并回读——#013 只是形成了待执行脚本，执行前线上库仍然只有原有 7 张表（`pg_tables` 与 `list_tables` 均已确认不存在这两张表）。

**执行内容**

按 `data/migrations/2026-09-23-project-inspiration-phase1.sql` 在线上库（应用 `wbapp_az0Z1pxT1CjCvbUNffduqc`）执行 10 条语句，**逐条成功，每条均返回空结果**：

| # | 语句 |
|---|---|
| 1 | `create table projects` |
| 2 | `create table project_items` |
| 3 | `create index projects_status_updated_idx on projects (status, updated_at desc)` |
| 4 | `create index project_items_project_order_idx on project_items (project_id, sort_order, saved_at desc)` |

**执行方式的一处硬性偏差（必须记下）**

云数据库的 SQL 执行通道**单次只接受一条语句**，多条会返回 `cannot insert multiple commands into a prepared statement`。因此脚本里的 `begin; … commit;` **无法作为单个事务整体执行**，实际是 10 条独立语句依次提交，**不具备原子性**：中途失败会留下半完成状态，且 `create table` / `create index` / `create policy` 都不是幂等写法（无 `if not exists`），重跑前需人工判断已完成到哪一步。

本次 10 条一次性全部通过，未出现半完成状态，所以没有触发该风险。**但如果将来要在已有数据的表上做不可逆 DDL，必须先解决"无事务 + 不幂等"这件事**（例如先本地演练、或改成 `drop policy if exists` + `create policy` 的幂等写法）。

**回读证据**

1) **结构**（脚本回读 1）
```sql
select tablename from pg_tables
where schemaname = 'public' and tablename in ('projects', 'project_items')
order by tablename;
```
→ 返回两行：`project_items`、`projects`。✅

2) **约束**（脚本回读 2）
```sql
select conrelid::regclass as table_name, conname, pg_get_constraintdef(oid) as definition
from pg_constraint
where conrelid in ('projects'::regclass, 'project_items'::regclass)
order by table_name, conname;
```
→ 返回 5 条，与脚本设计逐条相符：✅
- `projects_pkey` = `PRIMARY KEY (id)`
- `projects_status_check` = `CHECK ((status = ANY (ARRAY['active'::text, 'archived'::text])))`

- `project_items_item_id_fkey` = `FOREIGN KEY (item_id) REFERENCES items(id) ON DELETE CASCADE`

3) **权限／RLS**（脚本回读 3）
```sql

join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relname in ('projects', 'project_items');
```
→ `project_items` / `projects` 均 `relrowsecurity = true`。另用 `pg_tables.rowsecurity` 交叉验证：public 下 9 张表**全部** `true`。✅

```sql

where grantee = 'anon' and table_name in ('projects', 'project_items')
order by table_name, privilege_type;
```
→ 两张表各返回 `SELECT` / `INSERT` / `UPDATE` / `DELETE` 四项，齐全。✅

- **索引**：`pg_indexes` 确认三个新索引定义与脚本一致（`project_items_item_id_idx`、`project_items_project_order_idx`、`projects_status_updated_idx`）。

## #019｜2026-09-23｜翻阅页首次装配的入场滑动（意外动效）

**背景**

一期验证台报出「@1440／@768／@390 中央主卡水平居中（±1.5px）」三条失败，偏移分别是 36.29／11.66／6.54px，且**三档互不相同**。用一次性只读探针（复刻验证台的 iframe 环境，按 120ms 间隔连采 12 次）定位真因。

**证据**

- 三条失败**不是版式偏心**：同一时刻 `#cards` 的中心恒等于视口中心（1440→720、768→384、390→195），`stage`／`deckbox` 也都对称（1440 档 `deck-page[0,1440]`、两侧栏各 196px）。
- 偏移**随时间衰减**：1440 档 `145.27 → 36.29 → 4.65 → 0`，约 360ms 归零；768／390 同形。这正是 `.d-card` 上那条 `.34s` 过渡在跑。
- 起点偏移 168px = 主卡宽 336 的一半：`.d-card` 的 CSS 默认 `transform` 是 `none`，而首次 `layout()` 会写成 `translateX(calc(-50% + 0px))`。在 `none` 状态下卡片中心落在 `left:50%` 再右移半张卡宽的位置。

**结论**

验证台量在了过渡中间（量测口径问题，见 #020）；同时它暴露出一个**真实缺陷**：翻阅页每次首次渲染，整叠牌都会从右偏半张卡宽滑到居中——包括从详情页返回时。PRD 只要求拖拽／回弹／翻页有过渡，**没有入场动效**，这一滑是意外产物。

**本次变更**

- `projects.css`：新增 `.deckcards.booting .d-card{transition:none !important}`。
- `projects.js`：装配前给容器加 `booting`，在 `readGeom(); syncNodes(); layout(); paint();` 之后**同步**收口——`void cardsBox.offsetHeight`（逼一次同步样式解析，让最终 `transform` 在过渡被禁用的状态下就被采纳），紧接着 `cardsBox.classList.remove('booting')`。

**为什么收口必须是同步的**

第一版把摘类放在 `requestAnimationFrame` 里，实测偏移只从 168 降到 103／62／47px——**只减半，没消掉**。原因是 `readGeom()` 里的 `getComputedStyle` 已经强制过一次样式解析，而那一次卡上的 `transform` 还是 `none`；等下一帧摘类时过渡属性恢复，「none → 目标值」就被判成一次变更并打上 `.34s` 过渡。改成同步收口后再测：三档宽度**首帧偏移全部为 0**。

**回归（证明该有的动画没被误伤）**

- 翻页后立刻读到中央卡 `cx = 832 = 750 + 82`（正在走过渡），540ms 后落回 750，`index` 0→1，进度文案「第 2 / 14 张」。
- `#cards` 装配后的 class 为 `deckcards`，**无 `booting` 残留**（残留会让之后所有翻页变成瞬移）。
- 验证台补两条对应守卫：#020 记录的源码断言（CSS 规则 + JS 同步收口），以及每个宽度下「装配后没有留下 booting 类」。

**实现中挖出的两个真缺陷（都不是猜的，都是实测撞出来的）**

2. **缩略图异步到达时会把翻面弹回正面。** `renderNode()` 原来无条件 `setFlipped(false)`；而缩略图是 `cardsByIds()` 异步往返回来后才重画的，所以「翻到背面 → 图回来了 → 无声弹回正面」，表现是「点了卡片没反应、再点一次又好了」。修法：只有**换素材**才复位（`var same = n.itemId === it.id && isFlipped(n.el)` → `setFlipped(n.el, same, true)`）；节点被回收给别的素材时 `itemId` 已被清零，`same` 必为 false，仍会老老实实回正面。

## #023｜2026-09-23｜触控板双指横滑 = 翻页（桌面端等价操作）

**背景**

用户报：「电脑端有一个问题，我在笔记本触控板上，翻卡片的动作无法用触控板来操作，比如我的 Mac 不能够双指左右滑动来实现翻页。」

**根因**

牌堆只监听了 `pointerdown／pointermove／pointerup`，而 **macOS 触控板双指左右滑发出的是 `wheel` 事件（`deltaX`）**，不是指针拖拽——所以那套监听完全收不到。实测连发 3 次 `deltaX=120`，队列一动不动、页面也不滚（`deltaX` 被当作横向滚动，而容器本来就不横向滚动）。这也解释了为什么「鼠标按着拖」能用、触控板不行。

**本次变更**

`app/projects/projects.js`：在 `#stage` 上新增 wheel 监听，把滚轮翻译成与拖拽**同一套**的位移与判据。

- 累积 `deltaX` 到 `wAcc`，位置取 `rubber(wAcc * WHEEL_SCALE, step, .4, step*2)`——复用 #021 的分段阻尼，不另写一份。
- `WHEEL_SCALE = .55`：触控板一次轻扫轻松到 ±300，1:1 会一帧撞上阻尼上限，手感变成「一碰就到底」。
- `WHEEL_IDLE = 130ms`：多久没有新的 wheel 就当作手势结束；结束时用与 `onUp` **逐字相同**的两档判据（位移过 `step×0.3`，或甩得够快 `MIN_FLICK + |v|≥.38`）决定翻页还是回弹。
- `deltaMode` 折算（1=行 ×16，2=页 ×400），否则外接滚轮会慢 16 倍。
- 只吃「横向为主」的手势（`|dx| <= |dy|` 直接 return，**在 `preventDefault()` 之前**），纵向留给页面与背面的长总结。
- `preventDefault()` 顺手挡掉 Chrome 的双指前进／后退。
- `onDown` 里清掉挂着的滚轮定时器：否则手指按下后 130ms，那个定时器会拿着上一次滚轮的位移再 commit 一次，变成一次莫名其妙的翻页。
- `commit()` 的复位逻辑自动覆盖滚轮路径（同 #022）。
- 监听用 `{ passive: false }`——要 `preventDefault()` 就不能是 passive。

**理由**

- **复用同一套阈值，而不是给滚轮单写一份。** 同一台机器上「鼠标拖」和「双指滑」应当是同一个手感；两份数字迟早会漂。
- **速度档取整段手势的平均速度**（`dragX / (now - wT)`），不取相邻两次的瞬时速度：滚轮是一次次跳着来的，`dt` 可能只有 1–2ms，瞬时速度噪声太大。
- **`WHEEL_IDLE` 用「空闲判据」而不是 `wheelend` 事件**：`wheelend` 不是标准事件，Safari 不认。

**验证**

- **真实 wheel 事件**（CDP `Input.dispatchMouseEvent type:mouseWheel`，事件是 trusted 的）：1440 宽下 `dx=120 ×3`（间隔 40ms）→ `index 3→2`，结束后 `#cards` 不带 `dragging`。
- **组合场景**：先真实点击翻到背面（`flipped=true`）→ 横向滚轮 → `index 2→1` **且** `flipped=false`（「先复位再翻页」在滚轮路径同样成立）。
- **纵向放行**：`dy=120 ×3` → `index` 保持不变（1）。
- 桌面与手机两档的既有拖拽/阈值断言全部保持通过。
- `app/_verify_projects.html`：**143 条／143 通过／0 失败／0 跳过**（与 #022 同一次运行）。

**影响范围**

`app/projects/projects.js`、`app/_verify_projects.html`、`features/项目灵感筛选/PRD.md`（P2-2）。

**未改动内容**

`store.js`、`data/schema.sql`、任何页面 HTML、发布件、公开仓库、线上应用。未发布，未推送 Git。

**下一步**

与 #022 一起验收（人工过一遍翻阅页的翻面与触控板手势）→ 再单独讨论发布与 Git 推送。

## #024｜2026-09-23｜点旁侧卡＝滚到那一张（不翻面）

**背景**

用户本机实测两条反馈，这是第一条：

> 点击旁侧的卡片也会翻转，而且不会翻转回来，这个不对，点击旁侧卡片应该是先自动滚到对应的卡片，而不是翻转。

**根因（两层，缺一不可）**

1. **`layout()` 里那句 `pointerEvents = center ? 'auto' : 'none'` 是假防线。** 卡片本身是个透明的盒子，两个面（`.dc-front` / `.dc-back`）把它盖满，而**两个面自己写着 `pointer-events:auto`**。CSS 里**子元素的 `auto` 会覆盖祖先的 `none`** —— 于是给卡片设 `none` 完全拦不住侧卡的点击，命中测试照样落在面上的元素上。这句代码写在 #022 里，本意是「只有中央卡可点」，实际一次都没生效过。
2. **click 处理器没区分中央卡与侧卡。** 它在处理完爱心／详情／「吞掉拖动后那一下 click」之后，直接执行 `setFlipped(card, !isFlipped(card))`。侧卡既然接得到点击（见第 1 条），就会走进这一句 —— 表现就是用户说的「点侧卡也翻面」。而**侧卡翻面后会被布局重新摆到侧位、永远回不到中央**，所以看起来「翻不回来」。

**本次变更**

`app/projects/projects.js`：

- **删掉 `layout()` 里那句 `pointerEvents`。** 真正的命中目标永远是「当前可见的那一面」，不该在卡片这一层再装一道假防线。删掉后侧卡**是故意可点**的：点它＝「我要看这一张」。
- 新增 `qiOf(card)`：把 DOM 节点反查成队列序号。牌的 DOM 会被回收复用，所以**按「哪个节点」反查，不能按 `data-item`**（回收后属性可能指向旧素材）。
- **新增唯一出入口 `goTo(ni)`**：跳到队列里任意一张。拖拽松手、右下角上一张／下一张、点侧卡三条路都过它；「先复位再翻页」（P2-11）的复位写在它里面，绕不过去。`commit(dir)` 退化成 `goTo(d.index + dir)`。
- click 处理器改成：爱心 → 详情 → 吞 click → **侧卡 `goTo(qi)`** → 中央卡才 `setFlipped`。爱心／详情只认中央卡。
- `n.el.tabIndex` 仍是「中央卡 0、侧卡 −1」：侧卡可点但**不进 Tab 序列**，键盘用户的等价操作是方向键（`ArrowLeft` / `ArrowRight` → `commit` → `goTo`）。

**理由**

- **不能用「给侧卡加 `pointer-events:none`」来修。** 那样确实不翻了，但同时把「点侧卡跳过去」这个用户明确要的交互一起废掉 —— 那正是这条需求的正面要求。

- **可点范围与可聚焦范围不再相同**，所以旧断言「可聚焦范围 = 可点范围」被改写，如实分成两条：侧卡可点、但可聚焦的只有中央卡当前可见那一面的按钮。

**验证**

## #025｜2026-09-23｜滚轮从「一次甩动」改为「连续滚动」

**背景**

同一条反馈的第二条：

> 还有滑动好像没有很跟手，发现两侧滑不过去。

**根因**

#023 把一趟滚轮手势当成**一次甩动**处理，三个设置叠在一起造成「不跟手 + 滑不过去」：

- `WHEEL_SCALE = .55` —— 手势走 100px 卡片只跟 55px，是「打折跟手」；
- 位移取 `rubber(wAcc * .55, step, .4, step*2)` —— **封顶在 `step*2`**；
- 整趟手势只在**结束时判一次方向**，最多翻一张。

**实测数据（改前）**：手势 40px → 卡片 22px（比 **0.55**）；260px → 106px（比 **0.41**）；520px → **164px 封顶**（比 **0.31**），且只翻 **1** 张。520px 已经超过 6 格，用户得到的是「滑到一半就不动了」。

**本次变更**

`app/projects/projects.js` 的 wheel 处理函数按**连续滚动**重写：

- `WHEEL_SCALE = 1`：位移与手势 **1:1 跟手**，不打折。
- `wAcc` 累积 `deltaX`，`pages = Math.trunc(wAcc / step)` —— **走满几格就当场翻几张**（不封顶）；翻完只扣除**真正翻过去的格数**（`wAcc -= (d.index - ni) * step`），余量跨事件继续累积。
- 到达队列两端时 `ni` 夹住、余量清零（不越界）。
- 手势结束时 `wheelEnd()` 把不足一格的余量回弹到整格（复用既有的 `rebind()`），并摘掉 `.dragging`。
- **`rubber()` 不再参与滚轮路径**（它仍给真手指拖拽用）。两条路径**不再共用数字** —— 这一点推翻了 #023 的「共用同一套判据」。
- `onDown` 里清掉挂着的滚轮定时器并清零 `wAcc`，避免按下后 130ms 定时器拿旧位移再 commit 一次。

**理由**

- **「跟手」的定义就是 1:1。** 0.55 的手感本质是「卡片永远追不上手指」，用户描述成「不太跟手」是准确的。
- **封顶是为了「别把卡片甩出屏幕」，而连续滚动里这个顾虑不存在**：每走满一格已经翻了一张，位移与新索引互相抵消，卡片位置始终连续。
- **余量跨事件累积是必须的**：触控板一次双指滑会发几十条小 `deltaX`，单条常常远小于一格；按单条判「不足一格就清零」会导致**永远翻不了页**。

**验证**

- **真实浏览器实测（CDP 真实 wheel 事件 + 合成事件两条路）**：跟手比 **1.00**（手势 −80px → 卡片实际渲染位移 −80px）；520px 的手势翻 **4** 张（改前 1 张）；一路滑到底停在最后一张（`index 13 / 上限 13`），不封顶也不越界；反向滑动按格数翻回。
- 组合场景：翻面状态下横向滚动 → **先复位翻面、再按格数翻页**（P2-11 在滚轮路径同样成立）。
- 边界：总位移不足一格（63px < 82px）→ 不翻页、余量回弹；纵向滚动 → 不翻页。
- `app/_verify_projects.html`：**157 条／157 通过／0 失败／0 跳过**。验证台里 #023 的那批断言（「与拖拽共用同一套阈值」「不足阈值不翻页」按旧公式算）已全部按新模型重写。

**影响范围**

`app/projects/projects.js`、`app/_verify_projects.html`、`features/项目灵感筛选/PRD.md`（P2-2 改连续滚动、P2-2b 限定为只约束拖拽）。

**未改动内容**

`store.js`、`data/schema.sql`、`app/projects/projects.css`、任何页面 HTML、发布件、公开仓库、线上应用。未发布，未推送 Git。

## #026｜2026-09-23｜验证台自身加固（本轮暴露的三处）

**背景**

修 #024／#025 的过程中，验证台连续给出三种**不诚实**的表现，都不是被测代码的问题，而是验证台自己的问题。这类问题最危险：它的表象是「没有结论」，很容易被当成「还在跑」。

**三处缺陷**

1. **断言读了不存在的东西，整轮静默死在半途。** 侧卡断言用了 `__deck().nodes[i].el` —— 而 `Elangit.projects.__deck()` 是**裁剪过的快照**：`nodes` 里只有 `qi / itemId / hidden / opacity / z / cx / top / w / h`，**没有 `el`**（顶层也没有 `dragX`）。读 `undefined` 后 `.dispatchEvent` 抛错，异步函数中断，表格停在 142 行、`#note` 永不写入、汇总永远空白。
2. **`try{}` 把函数声明包成了块作用域。** 为了让「抛异常也留痕迹」加了一层 `try`，起点写在了 `'use strict'` 之后 —— 严格模式下**块内的函数声明是块作用域的**，于是 `g / ok / sk / push / summary / finish` 全被关进 `try` 块，收尾处报 `finish is not defined`。表象与第 1 条一模一样：表格有 164 行、没有任何结论。
3. **收尾提示谎报「未创建」。** `finish()` 里写 `(tmpId ? '#'+tmpId+'（已在收尾删除）' : '未创建')`，而收尾成功时 `tmpId` 已被清成 0 —— 「建了又删」和「根本没建」被报成同一句话。

**本次变更**

`app/_verify_projects.html`：

- 整轮包一层 `try / catch`，**起点放在所有函数声明之后**（`loadSrc()` 定义完再开），catch 里 `push` 一条红色断言并照常收尾。
- 收尾处再包一层 `try`，`finish()` 自身抛错时把原因写进 `#note`；末尾写 `document.body[data-verify-done]` 作为**机器可读的完成标记**。
- 在收尾前加一条**正向断言**「整轮跑完并到达收尾」—— 表格停在半途时不会有这一行。
- 新增 `tmpDeleted` 标记，`#note` 如实区分「已在收尾删除」与「**未删除，需手动清理**」。
- 跟手比改量**卡片实际渲染位移**（`getBoundingClientRect` 的 `cx`），不读内部变量 —— 手势期间 `.deckcards.dragging` 关掉了过渡，rect 是即时的，而且「跟手」这件事本身就是渲染结果。
- 修掉两处随实现作废的判据：`centerCard()` 的兜底分支（原来靠 `style.pointerEvents === 'auto'`，该值现在恒为空串，兜底永远返回 null）、几何探针里的「只有中央卡接收点击」（侧卡现在**故意**可点，改数「视觉上正好一张 `opacity=1` 的中央卡」）。
- 断言里加注释说明 `__deck()` 是快照、有哪些字段，避免下一个人再摸不存在的字段。

**理由**

- **验证台的失败必须是「可见的失败」。「没有结论」不是一种结论**，而它恰好是这套工具最容易产生、也最容易被误读的状态。三处缺陷的表现完全一致（表格有内容、汇总空白），值得一次修透。
- **正向标记比反向断言更可靠。** 「整轮跑完」这一条只要出现就说明跑到了底；只靠「失败数为 0」判断不了「跑到一半就死了」。

**验证**

- 加固后连续多次运行均**正常收尾**（`data-verify-done = 1`），汇总每次都被写入。
- 收尾提示实测输出：`本轮临时项目：#20（已在收尾删除）`。
- 最终结果：`app/_verify_projects.html` **157 条／157 通过／0 失败／0 跳过**；`app/_verify_home_ui.html` **118 条／113 通过／0 失败／5 跳过**（与改动前逐项一致，属回归对照，该验证台本轮未改动）。
- 数据库回读：`items=17`、`projects=1`（用户自有 #9「11」）、`project_items=0`、无「【验证台】临时项目」残留。**排查中上一次卡死的运行在库里留下过一条 `#16 【验证台】临时项目`（14:12 创建），已按测试痕迹当场清除。**

**影响范围**

**未改动内容**

## #041｜2026-09-24｜修飞入「从左往右的停顿」+ 削 3D rotateY（真机流畅度）

**背景**：#040 上线后用户真机反馈两条：① 「停止的时候卡片会从左往右的停顿」；② 「模拟器看上去很流畅，但是真机还是不够流畅」。两条根因都在 flyIn 动画。

**根因 1·从左往右的停顿**：`#040` 用的「flyDir 状态 + layout 写偏移位 + 350ms 后 layout 写标准位」方案被浏览器感知为**两段过渡**：snap 不调 layout → 新中央 el 保留「上帧 transform」；playFlyIn 设 flyDir=1 → 写「+44」→ 浏览器从「上帧值」过渡到「+44」反向跑 .34s；350ms 后清 flyDir=0 → 写「标准位 0」→ 浏览器又起一段「+44 → 0」.34s。两段中间看到的就是卡片停在「+44 偏移位」——**「从左往右的停顿」**.

**正确修法·单段正向过渡**：放弃 flyDir 机制，playFlyIn 改为**就地写 transform**——noanim 强制新中央 el 瞬时落到「偏移位」作为过渡起点 → reflow → 摘 noanim 恢复 .34s transition → 同步写「标准位」让浏览器感知 transform 变化入队「偏移位 → 标准位」单段 .34s 正向飞入。无 setTimeout、无 flyTimer、无 flyDir 状态。无反向、无停顿。

**根因 2·真机 3D 开销**：上一轮 #040 的飞入动画有 `rotateY(-10deg)`，iOS Safari 对带 rotateY 的 transform 每帧重算 3D 合成层（即使 transform 落定到无 rotateY 的标准位，过渡期间的 3D 矩阵重算+图片重新光栅化仍会让真机掉帧）。修法：**去掉 rotateY**，只保留 translateX + scale（都是 2D 合成器属性，不触发 3D 重算）。立体感变弱但保留「推进 + 放大」的飞入语言。

**验证证据**（真实浏览器 390×844 合成手势）：拖 2 格翻 2 张中央卡 transform 时间线 60~540ms 全为「标准位」（playFlyIn 同步写到标准位，CSS transition 在合成层播单段 .34s 「偏移位 → 标准位」）；`_verify_projects.html` 198/198/0/0 零回归。模拟器看不出旋转差异（无 3D 重算开销），**真机流畅度改善需要用户复测**——去掉 rotateY 后的 2D 合成开销是 iOS 真机掉帧的最大概率源。

**影响文件**：`app/projects/projects.js`（playFlyIn 重写、layout 飞入相关注释更新）、本记录、`docs/构建记录.md`。

**下一步**：请用户在真机复测：① 翻页落定是否还有「从左往右的停顿」；② 翻页那一瞬的「飞入立体感」是否还够（去掉 rotateY 比上一版平面了一些）。若仍不够再调「真机流畅度」可能要从其他路径切入（拖动期间 reserve-3d 的过渡状态、封面图 GPU 合成层数等）。
